# Trace-impact workflow

`engine/trace/impact` performs an offline, deterministic review-obligation
analysis for a caller-supplied snapshot of immutable artifacts, evidence,
dossiers, changes, evidence-digest changes, and optional model verdicts. It
does not read a repository by default, make network calls, execute a checker,
validate a model-to-implementation mapping, or infer relationships from labels,
paths, names, or similarity. Associations are made by exact stable IDs.

This workflow is a review and change-impact aid. A clean report means only that
the supplied snapshot contains no obligations recognized by this package. It is
not an implementation-conformance claim or a proof about unmodelled behavior.

## Exact dependency contract

Each evidence record must carry exactly one current, immutable dependency of
 each required artifact kind:

- `source` revision;
- `model` revision;
- `property` revision;
- `modelled-environment` assumption revision;
- `adapter` implementation revision and contract/schema version; and
- `checker` build revision and toolchain identity.

The evidence record also carries a lowercase SHA-256 digest of its exact
content. Dependency IDs and all identity fields must match the corresponding
artifact exactly. Unknown, duplicate, missing, or inexact mappings are rejected
or reported as obligations; the analyzer never guesses a replacement.

A changed artifact identity or changed evidence digest makes dependent evidence
`stale-evidence`. A removed or changed checker invalidates the checker/toolchain
identity just like any other dependency change. An unreferenced record is
`orphan-evidence`. A missing required kind is `missing-dependency` and also
blocks promotion of every model verdict that depends on that incomplete
evidence. `modelled-environment` describes only assumptions represented by the
model; it is not runtime or execution provenance.

## Model verdict provenance and authority

`ModelVerdict` records provenance for an executed model result. It must identify:

- a nonblank `ID` and `RunID`;
- the run's `RegistryRevision`;
- the `EngineBuildRevision` and `Toolchain`;
- one or more exact `EvidenceIDs`;
- the `CheckerArtifactID` that identifies the current checker build; and
- the `RegistryArtifactID` that identifies the registry artifact used by the
  snapshot.

`MappingApproved` is an explicit caller-supplied mapping gate. It is not inferred
from a matching name, path, model label, or verdict status. A verdict is
promotable only when all of the following remain true:

1. every referenced evidence ID exists and has complete exact dependencies;
2. every referenced evidence digest and dependency identity is current;
3. the checker artifact exists, is of kind `checker`, and its revision and
   toolchain exactly match the verdict;
4. the registry artifact exists and its revision matches `RegistryRevision`;
5. when `RunRegistryRevision` is supplied, it exactly matches the verdict's
   `RegistryRevision`;
6. `MappingApproved` is true; and
7. **every** evidence ID named by the verdict has applicable review coverage:
   an exact dossier target revision and scope, plus a nonblank reviewer decision
   that is applicable to that dossier.

The `RunID`, registry revision, checker identity, and mapping approval are
provenance assertions in the caller's offline snapshot. This package does not
resolve `RunID` in an external run registry, authenticate a registry, or prove
that the named registry or checker actually produced the evidence. The optional
`RunRegistryRevision` is a consistency assertion supplied by the caller, not an
external authority check. A checker used to execute the verdict need not be the
checker listed as a dependency of every evidence item: evidence may have been
generated by another checker. The exact checker relationship is represented by
the separate evidence dependencies and the verdict's checker provenance; this
workflow does not silently equate those IDs.

A verdict that fails any promotion gate receives `verdict-unpromoted`. A verdict
whose evidence, checker/toolchain, registry, or review mapping is no longer
current also receives `stale-verdict` with the applicable reason. These findings
are obligations, not evidence that the model result is false.

## Dossiers and policy-qualified renewal

A dossier names its exact target revision, scope IDs, evidence IDs, and reviewer
decision. A reviewer decision contains an ID, exact target revision and scope,
workflow, rationale, and explicit renewal rules. It applies only when target
revision and scope match exactly. A mismatch is a renewal obligation and does
not silently carry approval forward.

Renewal is policy-driven. A changed evidence digest or dependency produces a
`review-renewal` finding for a dossier only when that decision's recorded
`RenewOn` policy includes `dependency-change`. A scope or target mismatch is
renewable under the exact-scope rule and the recorded `scope-change` policy.
The analyzer does not manufacture a dependency-renewal rule, treat every stale
record as an automatic approval failure for the dossier, or infer policy from
workflow text. Regardless of dossier renewal policy, stale or incomplete
 evidence still prevents model-verdict promotion.

The only supported renewal rules are `dependency-change` and `scope-change`.
Unknown rules are invalid. A dossier with no decision, incomplete decision
fields, or a decision that does not exactly match its target and scope cannot
provide applicable review coverage.

## Deterministic findings and SARIF

`impact.Analyze` validates the complete snapshot and returns findings sorted by
kind and subject. Relevant finding kinds include:

- `missing-dependency` — required evidence dependency kind is absent;
- `stale-evidence` — evidence content or an exact dependency changed;
- `orphan-evidence` — evidence is not referenced by a dossier;
- `review-renewal` — the recorded review policy requires renewal;
- `stale-verdict` — verdict provenance, evidence, checker/toolchain, registry,
  or review mapping is stale; and
- `verdict-unpromoted` — one or more promotion gates are not satisfied.

`impact.SARIF` emits SARIF 2.1.0 with stable rule IDs such as
`trace-impact/stale-evidence` and a stable `findingId` property. A relative
`path:line` location is translated to a SARIF source location only when it is
unambiguous, including a repository-root file such as `main.go:12`; other
anchors remain artifact URIs without an invented line.

## Minimal API shape

The following is illustrative Go-shaped usage. It shows that a verdict is
checked against the complete evidence and artifact snapshot; it does not create
external authority or a conformance result:

```go
report, err := impact.Analyze(impact.Input{
    Artifacts:           artifacts,
    Evidence:            evidence,
    Dossiers:            dossiers,
    Changes:             changes,
    EvidenceChanges:     evidenceChanges,
    Verdicts: []impact.ModelVerdict{{
        ID:                  "verdict-1",
        RunID:               "run-1",
        RegistryRevision:    "registry-rev",
        EngineBuildRevision: "engine-rev",
        Toolchain:           "go-toolchain-rev",
        EvidenceIDs:         []string{"evidence-1", "evidence-2"},
        MappingApproved:     true,
        CheckerArtifactID:   "checker-1",
        RegistryArtifactID:  "registry-1",
    }},
    RunRegistryRevision: "registry-rev", // caller-supplied consistency assertion
})
if err != nil {
    return err
}
// Interpret report.Findings as obligations; do not turn a clean report into
// an implementation-conformance or model-correctness claim.
```

## Optional Git change acquisition

`impact.GitChanges` is optional. It accepts only two distinct lowercase full
40- or 64-hex commit IDs, resolves each exactly as a commit, and rejects a dirty
repository, including reported untracked files; ignored untracked files are
outside this cleanliness contract. The supplied repository must resolve to
the exact canonical working-tree root and must be an ordinary standalone local
repository. Linked Git directories and worktrees are unsupported: `.git` must
not contain `commondir` or `gitdir` metadata. The validator performs only the
existing non-recursive `Lstat` checks: when present, `.git/objects`, `.git/refs`,
`.git/info`, and `.git/logs` must be real directories; `.git/HEAD`, `.git/index`,
`.git/packed-refs`, `.git/info/exclude`, and `.git/info/attributes` must be
regular non-symlink files; and `.git/objects/info/alternates` is rejected.
Nested objects, refs, split-index files, and other descendants are not
recursively traversed or sandboxed. The caller must provide a trusted, stable
ordinary repository root. It invokes Git through
shell-free argv with explicit `--git-dir=<root>/.git` and
`--work-tree=<root>` pinning, external diff, text
conversion, replacement objects, optional locks, lazy fetch, repository
filters, and inherited `GIT_*` routing disabled case-insensitively, including
mixed-case names on Linux. Every Git invocation
sets `core.excludesFile` and `core.attributesFile` to the platform null device,
forces `core.fileMode=true`, and sets `GIT_ATTR_NOSYSTEM=1`, so caller global ignore/attributes files and
system attributes cannot alter acquisition. Windows fails closed
before starting Git. Before any `status` or `diff` command, the wrapper
case-normalizes and inspects local and `config.worktree` configuration files and
rejects executable filter/fsmonitor/diff controls, include or
conditional-include indirection, worktree configuration indirection, and
partial-clone or promisor controls. `core.worktree`, `core.excludesfile`, and
`core.attributesfile` redirections are rejected. If present, `.git/info/exclude`
and `.git/info/attributes` must be regular non-symlink files. The wrapper also
rejects `core.ignoreStat`, sparse-checkout controls, and
`extensions.sparseIndex`, and checks `git ls-files -v -z` before accepting
cleanliness; only the normal `H` tag is accepted, so `assume-unchanged`,
`skip-worktree`, and unknown index-state tags cannot hide a changed tracked
file. Configuration files must be regular files,
not symbolic links, and each read is capped by `GitOptions.MaxOutputBytes`. The
same option is an explicit per-command cap: it applies independently to each
Git invocation, including the complete `ls-tree` and `ls-files` NUL-delimited
preflight listings, rather than to their combined output. A zero value selects
the default 8 MiB cap; a positive value selects that many bytes. Oversized
preflight listings fail with a command-specific diagnostic.
On Linux, a no-follow, non-blocking open and descriptor identity check reject a
file replacement between metadata inspection and opening, including replacement
by a symbolic link or FIFO. This does not freeze file contents or protect
subsequent Git commands against concurrent repository writes. System and global
Git configuration is disabled, but explicit `--git-dir` and `--work-tree`
invocation bypasses Git's ordinary discovered-repository ownership check.
Acquisition does not enforce `safe.directory` or authenticate repository
ownership: the caller must authorize and trust the supplied repository root.
Both quoted subsections (`[filter "name"]`) and legacy dotted subsections
(`[filter.name]`) are checked. It also checks tree and index metadata for
submodules before `status`, then uses the Git submodule-ignore mode so Git never
traverses a submodule. This is a conservative rejection boundary: it does not
attempt to prove that a configuration file or submodule is harmless.

The caller must keep the repository and its configuration stable while Git
acquisition runs; the checks are not a filesystem snapshot or concurrent-write
sandbox. Git's local configuration parser may support versions newer than the
wrapper's conservative syntax checks, so unsupported controls are rejected
rather than interpreted. The repository therefore needs a Git version that
supports the command-line options used by the wrapper, including
`--no-lazy-fetch` (use a current Git, approximately 2.45 or newer).

Captured output, context, pipes, and the NUL-delimited raw stream are bounded
and handled deterministically. Raw diffs request `--no-abbrev`, and every
parsed object ID must be a full 40- or 64-hex ID. The parser accepts only `A`,
`M`, and `D` records; rename and copy statuses (`R` and `C`), type changes
(`T`), and submodule mode `160000` records are rejected. On Linux Git runs in a
dedicated process group; cancellation and output overflow terminate that group,
including descendants that remain in that process group, before the wrapper
returns. On normal completion, a descendant that inherits an output pipe can
delay wrapper completion until that descendant closes the pipe or the context
expires; the wrapper remains context-bounded. Once output streams are closed,
normal completion terminates that group. After context expiry, bounded process
cleanup may still run before the helper returns. The Linux exit-observation
loop has a fixed 30-second deadline before the ordinary `Wait` reap; this is
not an end-to-end cleanup deadline, and it does not bound the subsequent
`Wait` call. A descendant that deliberately calls
`setsid` or otherwise escapes the group is outside this containment guarantee. Linux observes leader exit with
`waitid(WNOWAIT)` before the ordinary `Wait` reap. The lifecycle marks reaping
under its mutex, terminates the group while the leader is still unreaped, then
releases the mutex before blocking in `Wait`; cancellation cannot signal after
reaping begins. Windows and non-Linux Unix targets fail closed before starting Git
because process-tree containment is not implemented there. This package makes
no subprocess-safety promise on those targets until an appropriate native
containment implementation and regression coverage are added.

Git output identifies changed paths only. `ChangesFromGit` requires a caller-
supplied one-to-one exact path mapping to immutable artifact replacement
identities. Deletions (`D`) require an explicitly removed mapping with
`Removed=true` and empty `Revision`, `ContractVersion`, and `Toolchain`;
additions and modifications must carry new immutable identities. Rename/copy metadata, type changes, and submodule mode
`160000` changes are rejected. The wrapper never uses path similarity or
creates mappings.

The G9 BDD Git helper registers cleanup when the scenario is initialized. It
restores the prior helper environment and removes acquired temporary directories
even when a later step fails.

## Scope

Use this workflow alongside the versioned trace ledger, model assumptions and
bounds, and an explicit human review process. Evidence, reviewer decisions,
model verdicts, and impact findings preserve provenance and obligations; none
of them by themselves establish implementation correctness.
