# Model check: mutex_flaw (Promela - examples/CH2/mutex_flaw.pml)

Коротко: требование «два процесса не должны одновременно попадать в критическую секцию» **на этой модели нарушается**. Движок нашёл контрпример из 15 шагов, в котором оба процесса проходят протокол входа и `cnt` становится равным 2. Класс причины — дефект самой системы (алгоритма): проверки `x`, `y`, `z` и записи в них чередуются, и каждая проверка может читать уже устаревшее значение. Тупиков в модели не найдено (исчерпывающий поиск, 429 состояний).

## 1. Summary

| ID | Свойство | Статус | Evidence | Кратко |
|---|---|---|---|---|
| P1 | `assert(cnt == 1)` в критической секции (проверка автора модели, строка 23) | `violated` | `exhaustive` | контрпример из 15 шагов (BFS, кратчайший); в DFS — 54 шага |
| P2 | отсутствие тупика (`deadlock`) | `verified` | `exhaustive` | поиск завершён полностью, 429 состояний, 858 переходов |
| P3 | инвариант `cnt <= 1` (требование пользователя, записанное напрямую) | `violated` | `exhaustive` | контрпример из 14 шагов — тот же сценарий, что у P1, без последнего шага `assert` |
| P4 | sanity: `cnt >= 1` достижимо (хоть кто-то входит в критическую секцию) | `verified` | `exhaustive` | свидетель из 7 шагов; требование не пусто |
| P5 | регрессионная метка: оба процесса одновременно стоят на `L7` | `verified` (достижимо) | `exhaustive` | свидетель из 12 шагов; это и есть дефект: оба прошли протокол входа |

Для P4 и P5 `verified` означает «состояние достижимо» (kind `reach`) — для P5 это подтверждение дефекта, а не хорошая новость.

## 2. Scope and assumptions

Пользователь недоступен для вопросов, поэтому незаданные поля карточки заполнены значениями по умолчанию, помеченными явно (`intake-card.yaml`, пометка `DEFAULT (assumed)`). Для учебного примера из корпуса это допустимо; для критической проверки их нужно подтвердить.

- **Граница системы.** Весь файл: два одинаковых процесса `user` (`active [2]`, `me = 1` и `me = 2`), общие байтовые переменные `x`, `y`, `z` (протокол входа) и `cnt` (сколько процессов сейчас в критической секции). Внешней среды нет — только планировщик. Ничего не исключено, файл не изменялся.
- **Семантика переходов.** Чередование (interleaving) одиночных операторов; каналов нет. Атомарный шаг — один оператор Promela одного процесса. *Умолчание (assumed):* в файле нет `atomic`/`d_step`, и модель намеренно показывает, что чтения и записи `x`, `y`, `z` чередуются; оборачивать их в `atomic` было бы проверкой другого алгоритма (`pitfalls.md` §6).
- **Терминальные состояния.** `end`-меток нет, процессы не завершаются (`goto L1`). *Умолчание (assumed):* любое состояние без включённых переходов — тупик и ошибка.
- **Справедливость (fairness).** `none`. Проверялись только свойства безопасности и достижимости, для них справедливость не нужна. Liveness («каждый желающий рано или поздно войдёт», отсутствие голодания) пользователь не запрашивал и не проверялось — см. §10.
- **Границы и ёмкости.** 2 процесса (задано файлом); `byte` для `cnt`, `x`, `y`, `z` — фактические значения 0..2, переполнения нет (движок остановился бы с `invalid-model`).
- **Отношение к реализации.** Модель написана вручную (учебный пример корпуса, глава 2). Реализации нет; результат — утверждение о модели, а не о какой-либо программе.

## 3. Model

- **Переменные состояния:** `cnt`, `x`, `y`, `z` : `byte` (глобальные); `user:0.me = 1`, `user:1.me = 2` : `byte` (локальные константы). Вектор состояния — 9 байт.
- **Процессы:** `user:0`, `user:1` — один и тот же `proctype` с метками `L1`–`L7`:
  `L1: x = me` → `L2:` если `y != 0 && y != me` → назад на `L1`, иначе → `L3: z = me` → `L4:` если `x != me` → `L1`, иначе → `L5: y = me` → `L6:` если `z != me` → `L1`, иначе → `L7: cnt++; assert(cnt == 1); cnt--; goto L1`.
- **Начальное состояние:** единственное — все переменные 0, оба процесса на `L1`.
- **Таблица соответствия имён:** имена в IR совпадают с именами в исходнике (`cnt`, `x`, `y`, `z`, `me`, метки `L1`–`L7`); экземпляры процессов обозначаются `user:0` (`me = 1`) и `user:1` (`me = 2`). Индекс локации `L7` в IR — 6 (используется в P5 как `pc(i) == 6`). Каждый шаг трассы несёт `origin` с номером строки исходника.
- **Предупреждения парсера:** нет (`parse.stderr.txt` пуст); `printf`, never-claim, каналов в модели нет.

## 8. Counterexample

**Одной фразой:** после 15 шагов оба процесса находятся в критической секции — `cnt` становится 2, и `assert(cnt == 1)` (строка 23) нарушается; кратчайший сценарий из `check-promela-bfs.json`, свойство P1 (декодировано по `counterexample.steps` и `final_state`; `mc_explain` в CLI недоступен).

**Хронология** (процесс, оператор, строка исходника, изменения; `user:0` — `me = 1`, `user:1` — `me = 2`):

| Шаг | Кто | Оператор (строка) | Изменение | Куда пришёл |
|---|---|---|---|---|
| 1 | user:0 | `x = me` (5) | x: 0 → 1 | L2 |
| 2 | user:0 | `(y == 0 \|\| y == me)` (8) — y = 0, проходит | — | L3 |
| 3 | user:0 | `z = me` (10) | z: 0 → 1 | L4 |
| 4 | user:0 | `(x == me)` (13) — x = 1, проходит | — | L5 |
| **5** | **user:1** | **`x = me` (5)** | **x: 1 → 2** | L2 |
| 6 | user:1 | `(y == 0 \|\| y == me)` (8) — y всё ещё 0, проходит | — | L3 |
| 7 | user:0 | `y = me` (15) | y: 0 → 1 | L6 |
| 8 | user:0 | `(z == me)` (18) — z = 1, проходит | — | L7 |
| 9 | user:0 | `cnt++` (22) — **user:0 в критической секции** | cnt: 0 → 1 | — |
| 10 | user:1 | `z = me` (10) | z: 1 → 2 | L4 |
| 11 | user:1 | `(x == me)` (13) — x = 2, проходит | — | L5 |
| 12 | user:1 | `y = me` (15) | y: 1 → 2 | L6 |
| 13 | user:1 | `(z == me)` (18) — z = 2, проходит | — | L7 |
| 14 | user:1 | `cnt++` (22) — **user:1 тоже в критической секции** | cnt: 1 → 2 | — |
| 15 | user:0 | `assert(cnt == 1)` (23) — **нарушение** | — | — |

Конечное состояние: `cnt = 2`, `x = 2`, `y = 2`, `z = 2`, `user:0.me = 1`, `user:1.me = 2`.

**Первая причинная развилка — шаг 5.** После шага 4 `user:0` уже убедился, что `x == me` (`L4`), но ещё не записал `y` (`L5`). Планировщик даёт ход `user:1`, и тот перезаписывает `x := 2`. С этого момента проверка `user:0` на шаге 4 опирается на устаревшее значение, а `user:1` на шаге 6 проходит проверку `y == 0`, потому что `user:0` ещё не успел выставить `y = 1`. Если бы после шага 4 продолжил `user:0` (`y = 1`), то `user:1` на `L2` увидел бы `y = 1 ≠ 0` и `≠ 2` и вернулся бы на `L1` — нарушения не было бы. Дальше (шаги 7–14) оба процесса просто доводят свои проверки до конца: каждый видит «свои» значения, потому что каждый проверяет переменную, которую другой либо уже перезаписал его же значением, либо ещё не трогал.

**Класс причины — дефект системы (алгоритма).** По процедуре `counterexamples.md` §3:
1. Формула соответствует требованию: `cnt` считает процессы в критической секции, `assert(cnt == 1)` и `cnt <= 1` — прямое выражение «не более одного». Не дефект свойства.
2. Ни один шаг трассы не делает того, чего не может реальная система с общими переменными: каждый шаг — одно чтение-сравнение или одна запись, чередование одиночных операторов допустимо. Модель не переаппроксимирует систему (никаких потерь, ёмкостей, отсутствующих блокировок в файле не заявлено). Не дефект модели.
3. Справедливость не участвует: контрпример конечен, никого не морят голодом. Не артефакт fairness/среды.
4. Следовательно — дефект системы: протокол входа на `x`, `y`, `z` проверяет флаги по одному, и между проверкой и следующей записью другой процесс может изменить проверенную переменную; проверка «check-then-act» не атомарна.

P3 (инвариант) даёт тот же сценарий без шага 15 — `cnt = 2` уже после шага 14; P5 (оба на `L7`) достигается за 12 шагов (те же шаги 1–8, 10–13): это состояние, где оба прошли протокол входа, ещё до всякого `cnt++`. Одной трассы достаточно (свойства состояния, не CTL). DFS находит другой, более длинный контрпример (54 шага) — это не противоречие, оба корректны.

## 9. Limitations

- Результат — утверждение о **модели** `mutex_flaw.pml` при перечисленных допущениях, а не о какой-либо реализации; перенос требует отдельного аргумента о соответствии (его здесь нет и он не заявляется).
- Поле «атомарный шаг = один оператор» и «тупик = ошибка» — умолчания, не подтверждённые пользователем. Если в реальной системе проверки и записи `x`/`y`/`z` неделимы (например, аппаратный CAS), это уже другой алгоритм и другая модель; на этой модели ответ от этого не меняется.
- Проверялись только safety (P1–P3) и достижимость (P4–P5). Liveness — «процесс, желающий войти, рано или поздно войдёт» / отсутствие голодания и живой блокировки — не проверялась: пользователь не просил, а в этой сборке движка `ltl`/`progress` не исполняются (G4). Заметьте, что оба процесса могут бесконечно крутиться в цикле `L1`–`L6` — это вопрос к liveness, а не к safety, и он остаётся открытым.
- Поиск нередуцированный (POR нет), но полный: 429 состояний — весь достижимый граф (подтверждено `--sweep`).
- `mc_simulate`, `mc_lint_property`, `mc_explain`, `mc_manifest` не имеют CLI-эквивалентов: симуляция пропущена (её роль — sanity — сыграли P4/P5), классификация свойств и декодирование трассы выполнены вручную по отчётам, манифест собран вручную.
- Сравнение счётчика состояний с SPIN (`pan -c0`) не выполнялось: SPIN в проекте только оракул тестов движка, для ответа он не нужен.

## 10. Next actions

1. **Исправить алгоритм, не требование.** Гипотеза для проверки: заменить протокол входа на корректный алгоритм взаимного исключения для двух процессов (в корпусе есть `CH2/peterson.pml` — алгоритм Петерсона с `flag[]` и `turn`), либо ввести общий атомарный примитив там, где реальная система действительно его имеет. Оборачивать `L1`–`L6` в `atomic` «чтобы тест прошёл» нельзя — это проверило бы другой алгоритм (`pitfalls.md` §6).
2. После любого изменения модели прогнать **все** свойства заново (P1–P5), не только P1: P5 должно стать недостижимым (`reach` → `violated`, что для регрессионной метки означает «сценарий исключён»), P4 должно остаться достижимым (иначе исправление «работает», потому что никто не входит), P2 (тупик) — остаться `verified`.
3. Если нужна гарантия входа (отсутствие голодания), сформулировать liveness-свойство и до запуска договориться о справедливости (weak fairness движок поддерживает с G4; strong — нет); отчёт должен показывать результат и без справедливости, и с ней.
4. Если модель претендует на описание реальной программы, добавить аргумент соответствия (какие операторы Promela каким операциям кода отвечают и почему их гранулярность совпадает).
