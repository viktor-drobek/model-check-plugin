# Проверка модели `Promela - examples/CH2/mutex_flaw.pml`

## Вывод

**Свойство нарушается.** Модель не обеспечивает взаимное исключение: существует
последовательность из 14 шагов, после которой оба процесса `user` одновременно
находятся в критической секции (`cnt == 2`), и встроенная проверка
`assert(cnt == 1)` в строке 23 срабатывает.

Проверка выполнена Spin 6.5.2 полным перебором пространства состояний
(safety-режим, всего 429 состояний при исчерпывающем обходе); в пространстве
состояний 8 различных состояний с нарушением assert.

## Что проверялось

Модель (не изменялась, скопирована в `mutex_flaw.pml` рядом с этим файлом):

```promela
byte cnt;
byte x, y, z;
active [2] proctype user()
{	byte me = _pid + 1;	/* me is 1 or 2 */
L1:	x = me;
L2:	if
	:: (y != 0 && y != me) -> goto L1
	:: (y == 0 || y == me)
	fi;
L3:	z = me;
L4:	if
	:: (x != me)  -> goto L1
	:: (x == me)
	fi;
L5:	y = me;
L6:	if
	:: (z != me) -> goto L1
	:: (z == me)
	fi;
L7:	/* success: enter critical section */
	cnt++;
	assert(cnt == 1);
	cnt--;
	goto L1
}
```

Требование «два процесса не должны одновременно попадать в критическую секцию»
уже закодировано в модели самим автором: счётчик `cnt` увеличивается при входе в
секцию и уменьшается при выходе, `assert(cnt == 1)` утверждает, что в секции
ровно один процесс. Именно это утверждение и проверялось.

## Как проверялось

```
spin -a mutex_flaw.pml
gcc -O2 -DSAFETY -o pan pan.c          # поиск в глубину
./pan -E                               # -> assertion violated (cnt==1), depth 53
gcc -O2 -DSAFETY -DBFS -o pan_bfs pan.c
./pan_bfs                              # поиск в ширину -> кратчайший контрпример, depth 14
spin -t -p -g -l mutex_flaw.pml        # воспроизведение трассы
./pan -c0 -n                           # исчерпывающий обход, подсчёт всех ошибок: errors: 8
```

Логи: `pan_run.log`, `pan_bfs_run.log`, `pan_all_errors.log`, трассы
`trail.log` (54 шага, DFS) и `trail_shortest.log` (14 шагов, BFS), файл
`mutex_flaw.pml.trail` — трасса Spin для кратчайшего контрпримера.

## Кратчайший контрпример (14 шагов)

P1 — процесс с `me = 1` (`_pid 0`), P2 — с `me = 2` (`_pid 1`).
Начальное состояние: `x = y = z = cnt = 0`.

| Шаг | Процесс | Действие                       | Состояние после шага   |
|----:|---------|--------------------------------|------------------------|
|  1  | P2      | `L1: x = 2`                    | x=2 y=0 z=0            |
|  2  | P2      | `L2: y == 0` — проход          |                        |
|  3  | P2      | `L3: z = 2`                    | x=2 y=0 z=2            |
|  4  | P2      | `L4: x == 2` — проход          |                        |
|  5  | P1      | `L1: x = 1`                    | x=1 y=0 z=2            |
|  6  | P1      | `L2: y == 0` — проход (P2 ещё не записал y) |           |
|  7  | P2      | `L5: y = 2`                    | x=1 y=2 z=2            |
|  8  | P2      | `L6: z == 2` — проход          |                        |
|  9  | P2      | `L7: cnt++`                    | **cnt=1, P2 в секции** |
| 10  | P1      | `L3: z = 1`                    | x=1 y=2 z=1            |
| 11  | P1      | `L4: x == 1` — проход          |                        |
| 12  | P1      | `L5: y = 1`                    | x=1 y=1 z=1            |
| 13  | P1      | `L6: z == 1` — проход          |                        |
| 14  | P1      | `L7: cnt++`                    | **cnt=2, оба в секции**|
| 15  | P2      | `assert(cnt == 1)` — нарушение | cnt = 2                |

## Почему алгоритм не работает

Алгоритм пытается построить взаимное исключение на трёх «флагах» `x`, `y`, `z`
по схеме «записал своё значение — проверил, что оно не перезаписано». Но:

1. Ни одна проверка не является атомарной вместе с предшествующей записью
   другой переменной: между `L4` (P2 убедился, что `x == 2`) и `L5` (P2 запишет
   `y = 2`) есть окно, в котором P1 успевает записать `x = 1` и пройти проверку
   `L2`, потому что `y` всё ещё равно 0 — P2 «заявил о себе» только через `x`,
   а `L2` смотрит только на `y`.
2. После этого каждый процесс на `L4` и `L6` проверяет переменные `x` и `z`, которые
   сам же только что записал (шаги 10–13 для P1), и никакая из переменных не
   хранит информацию «в секции уже кто-то есть». Проверка `y` на `L2` делается
   один раз и слишком рано, а перепроверить `y` после `L5` алгоритм не пытается.

Иначе говоря, в протоколе нет переменной, которую процесс устанавливает *до*
всех проверок и которую другой процесс обязан увидеть; вход в секцию решается по
локально согласованным, но глобально устаревшим наблюдениям. Это учебный пример
«неправильного» решения из главы 2 книги Хольцмана о Spin (рядом лежат
`mutex.pml` и `peterson.pml` с корректными вариантами).

## Что стоит сделать

- Использовать проверенный алгоритм (например, Peterson: флаги `flag[2]` + общая
  переменная `turn`, см. `Promela - examples/CH2/peterson.pml`) или аппаратную
  атомарную операцию (`atomic { ... }` / test-and-set) для захвата ресурса.
- После исправления повторить `spin -a` + `pan` в safety-режиме: ожидается
  `errors: 0` при полном обходе. Дополнительно имеет смысл проверить отсутствие
  тупиков (`pan` без `-E`) и, если важна живость, прогнать с `-a` и claim
  на «каждый желающий в итоге войдёт в секцию».

## Ограничения проверки

- Проверялось только свойство безопасности «не более одного процесса в секции»
  (через существующий `assert`). Живость (отсутствие starvation) и отсутствие
  тупиков отдельно не проверялись: safety-обход показал 8 ошибок, все —
  нарушения этого же assert; недопустимых конечных состояний Spin не сообщил.
- Модель с двумя процессами; для N > 2 алгоритм не рассматривался.
