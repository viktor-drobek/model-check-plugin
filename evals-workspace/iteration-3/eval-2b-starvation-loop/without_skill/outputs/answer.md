# Процесс B: «рано или поздно выставит `done`» — так ли это?

**Короткий ответ: нет — не при всех допустимых прогонах. Свойство `<> done` нарушается.**
Оно становится истинным только если дополнительно предположить *слабую справедливость* (weak fairness) планировщика.

Модель: `model-check-plugin/engine/testdata/promela/starvation.pml`

---

## 1. Что в модели

```promela
bit done;

active proctype A()
{	bit t;
	do
	:: t = 1 - t
	od
}

active proctype B()
{
	done = 1
}
```

Два процесса запускаются одновременно:

* `A` — бесконечный цикл `do :: t = 1 - t od`; он **всегда разрешён** (enabled) и никогда не завершается;
* `B` — один-единственный шаг `done = 1`, он тоже **всегда разрешён** с самого начала и до момента, пока не выполнится.

Присваивание `done = 1` ничем не охраняется: `B` не ждёт ни канала, ни условия. То есть это не взаимная блокировка (deadlock) и не логическая ошибка в охране — это чистое *голодание* (starvation): `B` готов работать, но планировщик волен его не выбирать.

## 2. Почему свойство нарушается

Семантика Promela/SPIN по умолчанию — **чередование без каких-либо предположений о справедливости**. На каждом шаге планировщик выбирает любой разрешённый переход, и этот выбор ничем не ограничен на бесконечность.

Значит, существует легальный бесконечный прогон, в котором планировщик выбирает **только** `A`:

```
A: t = 1-t ; A: t = 1-t ; A: t = 1-t ; ...   (бесконечно)
```

`B` при этом навсегда остаётся в состоянии «готов, но не выбран», `done` остаётся `0`. Такой прогон — контрпример к `<> done`.

Заметьте: у `A` всего два локальных состояния (`t = 0` и `t = 1`), поэтому это настоящий **цикл в графе состояний**, а не бесконечно растущая трасса. Формально контрпример имеет вид «префикс + лассо»: пустой префикс и цикл из двух шагов `A`.

## 3. Проверка на SPIN

Я прогнал модель через установленный SPIN 6.5.2. К копии модели добавлено требование:

```promela
ltl eventually_done { <> done }
```

Артефакты прогона — в `outputs/spin-run/` (`starvation.pml` с добавленной LTL-формулой, сгенерированный `pan.c`, трасса `starvation.pml.trail`, `counterexample.txt`, `pan-fair.txt`).

### 3.1. Без справедливости

```
$ spin -a starvation.pml && gcc -o pan pan.c
$ ./pan -a -N eventually_done
pan:1: acceptance cycle (at depth 0)
pan: wrote starvation.pml.trail
...
	acceptance   cycles 	+ (fairness disabled)
State-vector 36 byte, depth reached 4, errors: 1
```

**Найден acceptance cycle — свойство нарушено.** Трасса контрпримера (`spin -t -p -g`):

```
  <<<<<START OF CYCLE>>>>>
Never claim moves to line 4	[(!(done))]
  2:	proc  0 (A:1) starvation.pml:11 (state 1)	[t = (1-t)]
  4:	proc  0 (A:1) starvation.pml:11 (state 1)	[t = (1-t)]
spin: trail ends after 4 steps
#processes: 2
		done = 0
  4:	proc  1 (B:1) starvation.pml:17 (state 1)   <-- B так и стоит на `done = 1`
```

Цикл состоит из двух шагов `A` (переворот `t` туда и обратно), внутри цикла `done = 0`, а `B` всё это время висит на строке 17, готовый выполниться. Это ровно тот сценарий, который описан выше.

### 3.2. Со слабой справедливостью

```
$ ./pan -a -f -N eventually_done
State-vector 36 byte, depth reached 4, errors: 0
        4 states, stored
        1 states, matched
```

**Ошибок нет — свойство выполняется.** Флаг `-f` накладывает слабую справедливость: процесс, который *непрерывно* разрешён вдоль суффикса прогона, не может быть проигнорирован навсегда. `B` непрерывно разрешён с момента старта и до своего выполнения, поэтому под weak fairness он обязан рано или поздно сделать свой шаг, и `done` становится `1`.

Слабой справедливости здесь достаточно — более сильное предположение (strong fairness) не требуется, потому что разрешённость `B` не мерцает: она непрерывна.

## 4. Итог

| Предположение о планировщике | `<> done` | Результат SPIN |
|---|---|---|
| Без справедливости (семантика Promela по умолчанию) | **ложно** | `pan -a` → acceptance cycle, 1 error |
| Слабая справедливость | **истинно** | `pan -a -f` → 0 errors |

Ответ на вопрос зависит не от кода `B`, а от того, что вы готовы предположить о среде выполнения:

* Если под «рано или поздно» имеется в виду *любое* допустимое поведение системы, включая произвольно недружелюбный планировщик, — **нет, `done` может никогда не выставиться**.
* Если вы работаете на реальной ОС с вытесняющим планировщиком или на любом рантайме, дающем слабую справедливость, — **да, `done` будет выставлен**, и это нужно зафиксировать как явное допущение модели, а не считать само собой разумеющимся.

Практический вывод: если гарантия прогресса `B` важна, полагаться на неё неявно нельзя. Её нужно либо вынести в документированное допущение модели (и проверять с `-f`), либо обеспечить в самой модели — например, ограничить число итераций `A` или добавить явную синхронизацию, при которой `A` уступает управление.

## Допущения (пользователь был недоступен для уточнений)

1. **Формализация вопроса.** «Рано или поздно выставит `done`» я формализовал как LTL-свойство `<> done` (eventually done). Альтернативное прочтение — «процесс `B` рано или поздно завершится» — даёт тот же ответ, поскольку единственный шаг `B` и есть `done = 1`.
2. **Базовая семантика.** Считал стандартную семантику Promela/SPIN: асинхронное чередование, отсутствие предположений о справедливости по умолчанию. Это же и есть источник расхождения между двумя ответами.
3. **Область проверки.** Проверял модель ровно в том виде, в каком она лежит в репозитории, добавив только LTL-требование. Сам файл в репозитории не изменялся — работа велась с копией в `outputs/spin-run/`.
4. **Инструмент.** Использовался системный SPIN 6.5.2, а не движок из этого репозитория, — как независимая проверка рассуждения.

Замечу, что комментарий в шапке самого файла описывает ровно это поведение; прогоны SPIN выше — независимое подтверждение, а не пересказ комментария.
