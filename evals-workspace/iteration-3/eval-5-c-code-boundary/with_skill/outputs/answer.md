# Model check: `Promela - examples/CH17/simple1.pr` (модель с `c_code`)

## 1. Сводка

**Файл в том виде, в каком он лежит в корпусе, движок не проверял.** Он использует
встроенный C (`c_code`, `c_expr`), а это конструкция вне подмножества Promela,
которое принимает движок (запрет на выполнение хост-кода, NFR-004). Парсер отклонил
вход на строке 1, отчёта не возникло, поэтому статус каждому свойству я присваиваю
сам:

| ID | Свойство исходного файла | Status | Evidence |
|---|---|---|---|
| P1 | `assert(c_expr { x==4 })` и `assert(c_expr { x==6 })` | `not-executed` | `unknown` |
| P2 | отсутствие тупика / недопустимого конечного состояния | `not-executed` | `unknown` |

Причина дословно из движка:
`construct outside subset: c_code (embedded C is outside the subset) (simple1.pr, line 1)`.

**Что было сделано вместо этого.** Я переписал модель внутри подмножества — эффект
каждого C-фрагмента выражен обычными присваиваниями и выражениями Promela
(`references/promela-subset.md` §3, колонка «Rewrite to offer»). Это **изменение
модели**, объявленное в §3; все вердикты ниже относятся к переписанной модели
`model/simple1-rewrite.pml` (sha256 `8dbf0034…`), а не к корпусному файлу.

| ID | Свойство переписанной модели | Status | Evidence | Счётчики |
|---|---|---|---|---|
| P1 | `assert` (оба утверждения модели) | `verified` | `exhaustive` | 8 состояний, 7 переходов, глубина 4 |
| P2 | `deadlock` | `verified` | `exhaustive` | 8 состояний, 7 переходов, глубина 4 |
| P3 | достижимость `x == 4` (через `[] !(x == 4)`) | `violated` → **достижимо** | `exhaustive` | 10 состояний продукта, 16 переходов |
| P4 | достижимость `x == 6` (через `[] !(x == 6)`) | `violated` → **достижимо** | `exhaustive` | 10 состояний продукта, 16 переходов |

Словами: на модели `simple1-rewrite.pml` при перечисленных допущениях контрпример не
найден ни для одного из двух `assert`, ни для тупика; поиск был исчерпывающим (8
состояний, весь достижимый граф развёрнут, `search.stop: "complete"`). Обе ветви
`if` действительно проходимы, то есть оба `assert` вычисляются, а не «выполняются
впустую». Для P3 и P4 слово `violated` — это хорошая новость: вопрос задан
отрицанием (см. §4 и §8).

## 2. Границы и допущения

- **Граница системы:** один процесс `simple` и одна целочисленная переменная `x`.
  Среды нет, модель замкнута; единственный недетерминизм — выбор ветви `if`.
- **Вне модели:** C-компилятор и хост-рантайм, которыми SPIN исполнял бы фрагменты
  `c_code`. Именно их этот движок принципиально не запускает.
- **Семантика переходов:** чередование (процесс один, так что фактического
  чередования нет); атомарный шаг — один оператор Promela.
- **Fairness:** `none`. Свойств живости не ставилось и не проверялось, поэтому
  допущение о справедливости в результат не входит.
- **Границы доменов:** `x` — `int` движка; достижимые значения 0, 2, 4, 6, поэтому
  вопрос о переполнении не возникает ни в одну сторону.
- **Отношение к реализации:** корпусный файл — учебная модель из главы SPIN про
  встроенный C, а не система. Переписанная модель — ручная модель, написанная мной.
  Перенос результата на какой-либо код потребовал бы отдельного аргумента о
  соответствии; такого аргумента здесь нет и я его не выдумываю.

### Явно помеченные допущения (пользователь был недоступен для вопросов)

Скилл предписывает спрашивать; вместо вопросов фиксирую значения по умолчанию.
Ни одно из них не подтверждено пользователем.

- **A1.** Цель — исчерпывающий результат на учебном примере, а не поиск бага и не
  ограниченная проверка.
- **A2.** Граница системы — процесс `simple` и переменная `x` (см. выше).
- **A3.** Атомарный шаг — один оператор. В оригинале каждый блок `c_code { … }` —
  один шаг SPIN; в переписи ему соответствует одно присваивание, то есть
  гранулярность сохранена.
- **A4.** Проверяемые требования — два собственных `assert` модели, отсутствие
  тупика (свойство добавляет фронтенд сам) и достижимость обеих ветвей.
- **A5.** Домен `x` — `int`; в оригинале это C `int`. Достижимые значения малы,
  расхождение политик переполнения (движок → `invalid-model`, C → перенос разрядов)
  не активируется.
- **A6.** `fairness: none`.
- **A7.** Меток `progress` в модели нет, поэтому поиск непрогрессивных циклов
  (`--progress`) не запускался: на модели без меток непрогрессивным оказывается
  любой цикл, и `violated` означал бы «метки не расставлены», а не «система висит».
- **A8.** Исключение C-рантайма из границы системы — моё решение, а не требование
  пользователя.
- **A9.** Файлы корпуса считаю публичными учебными материалами без секретов, поэтому
  модель, IR и трассы сохранены в каталоге `outputs/`.
- **A10.** *(рассуждение, не запуск)* В SPIN переменная, объявленная внутри
  `c_code { int x; }`, по умолчанию **не входит в вектор состояния** — её отслеживают
  только явными `c_track`/`c_state`. Значит, в переписи `x` стал наблюдаемой частью
  состояния, чего в оригинале не было. На исход двух `assert` здесь это не влияет
  (процесс один, чередования нет), но на число состояний влияет. Это моё
  рассуждение из документации SPIN: **запуском оно не проверено**, SPIN в этой
  сессии не устанавливался и не запускался.

### Модель как её прочитал движок

- **Переменные состояния:** `x : int`, начальное значение 0.
- **Процессы:** `simple:0`, один экземпляр (`active proctype`).
- **Переходы:** `x = 2`; затем недетерминированный выбор между
  (`x = x + 2`, потом `assert(x == 4)`) и (`x = x * 3`, потом `assert(x == 6)`);
  затем нормальное завершение процесса.
- **Начальное состояние:** `x = 0`, `simple:0` перед первым оператором.
- **Допустимые конечные состояния:** нормальное завершение `simple:0` (фронтенд сам
  пометил точку после `fi` как `end`).
- **Размер вектора состояния:** 6 байт.
- **Предупреждения парсера:** ни одного (stderr всех запусков пуст). В частности,
  нет `printf`, нет `never`-claim, нет меток `progress`/`accept`.

Соответствие имён «источник → модель» здесь тождественное: `x` → `x`,
`simple` → `simple:0`.

## 4. Свойства

| ID | Формулировка | Class | Logic | Формула | Атомы | Проверка на пустоту |
|---|---|---|---|---|---|---|
| P1 | «оба `assert` модели выполняются» | safety | invariant (собственные `assert` модели) | свойство движка `assert` | `x == 4`, `x == 6` | P3 и P4 показывают, что обе ветви достижимы, значит оба `assert` действительно вычисляются; отдельно проведён негативный контроль (§8) |
| P2 | «модель не зависает» | safety | deadlock | свойство движка `deadlock` (добавлено фронтендом) | — | — |
| P3 | «первая ветвь достижима, `x == 4` случается» | reachability | LTL | `[] !(x == 4)`, ожидаемый ответ `violated` | `x == 4` | сама является страховкой от пустоты |
| P4 | «вторая ветвь достижима, `x == 6` случается» | reachability | LTL | `[] !(x == 6)`, ожидаемый ответ `violated` | `x == 6` | то же |

Расширение у всех четырёх — `untimed`. Ни одного требования о времени или
вероятности в задаче нет.

**Почему достижимость задана отрицанием.** Вопрос «возможно ли `p`» экзистенциальный
и в LTL напрямую не выражается: LTL неявно универсальна. Каноническая форма —
проверить `[] !p` и прочитать `violated` как свидетельство
(`references/properties-ltl-ctl.md` §3, строка «it is possible that p», и §4
«Existence»). Поэтому `violated` у P3 и P4 — это подтверждение достижимости, а не
дефект. Свойства `reach` движка доступны только через MCP-слой (поле `properties`
в `mc_check`), которого в этой сессии нет, так что маршрут через `--ltl` —
единственный доступный из CLI.

`mc_lint_property` по той же причине недоступен: классификация свойств выше
**сделана вручную** по `references/properties-ltl-ctl.md` §1. Обе формулы
`X`-свободны, что движок подтвердил в записи `temporal`:
`stutter_invariant: true`.

Логику никто не подменял: требования пользователя были о конкретных состояниях
(safety + достижимость), CTL здесь не нужна — и не была бы исполнена: этой сборкой
`ctl` возвращается как `not-executed` (G5).

## 8. Контрпримеры

### P3 и P4 — свидетельства достижимости, а не дефекты

Обе трассы — лассо (`loop.start = 11`, `loop.steps = 2`). Из 12 шагов половина
принадлежит не модели: шаги процесса `never:ltl1` / `never:ltl2` — это claim-автомат
(в трассе он ходит первым на каждом шаге), а шаги процесса `-` — расширение
остановившейся системы повторением последнего состояния (stutter extension). Убрав
их, получаем настоящую хронологию модели.

**P3 (`x == 4`), шаги модели:**

| Шаг | Процесс | Оператор (строка) | Изменение |
|---|---|---|---|
| 2 | `simple:0` | `x = 2` (22) | `x: 0 → 2` |
| 4 | `simple:0` | `x = x + 2` (24) | `x: 2 → 4` |
| 6 | `simple:0` | `assert(x == 4)` (24) | — (утверждение истинно) |
| 8 | `simple:0` | `-end-` (27) | процесс завершается |

Конечное состояние: `x = 4`. Дальше система не может двигаться, и с шага 11 цикл из
двух шагов (переход claim-автомата плюс stutter) повторяется бесконечно — это
техническое продолжение остановившегося прогона, а не активность модели.

**P4 (`x == 6`), шаги модели:** те же, но шаг 4 — `x = x * 3` (строка 25),
`x: 2 → 6`, и шаг 6 — `assert(x == 6)`. Конечное состояние: `x = 6`.

**Класс причины:** ни системный дефект, ни дефект модели. Полярность формулы выбрана
намеренно: `[] !p` — единственный способ задать вопрос о достижимости в LTL, и
`violated` здесь есть ответ «да, достижимо». Оба `assert` в этих трассах проходят
успешно.

### Негативный контроль (проверка, что `assert` вообще проверяется)

Чтобы убедиться, что `verified` у P1 не получен «впустую», я сделал мутанта
`model/simple1-mutant-assert5.pml` — та же модель, но второе утверждение заменено на
заведомо ложное `assert(x == 5)`. Результат при BFS: `assert` → `violated`,
`exhaustive`, причина движка: `assert(x == 5) fails in the last step of the
counterexample`; контрпример из трёх шагов `x = 2, x = x * 3, assert(x == 5)`,
конечное состояние `x = 6`. Значит, свойство `assert` действительно исполняется и
способно падать; `verified` у оригинальной переписи содержателен. `deadlock` на
мутанте остался `verified` / `exhaustive`.

## 9. Ограничения

1. **Главное: ни один вердикт §7.2 не относится к файлу `CH17/simple1.pr`.** Они
   относятся к `model/simple1-rewrite.pml` (sha256 `8dbf0034…`) — другому артефакту,
   отличия которого перечислены в §3. Корпусный файл получил `not-executed` и
   больше ничего.
2. Эквивалентность оригинала и переписи **не доказана** — она обоснована построчным
   соответствием таблицы §3, то есть моим чтением, а не проверкой. В частности, шаг
   A10 (переменная `x` входит/не входит в вектор состояния) делает два объекта
   формально разными; на исход двух `assert` это здесь не влияет по аргументу
   «процесс один, чередования нет», но это аргумент, а не запуск.
3. Разница политик переполнения (движок → `invalid-model`, C → перенос разрядов) в
   этой модели не активируется, поскольку достижимые значения — 0, 2, 4, 6. На
   модели с большими значениями результаты движка и SPIN разошлись бы.
4. Поиск нередуцированный (нет POR, симметрии, абстракции) — здесь это несущественно
   (8 состояний), но это факт о методе.
