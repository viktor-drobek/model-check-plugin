# Обязан ли процесс B рано или поздно выставить `done`?

**Короткий ответ: нет — не обязан.** Утверждение неверно при стандартной (нечестной, *unfair*) семантике чередования Promela/SPIN. Оно становится верным только если дополнительно предположить **слабую справедливость** (weak fairness) планировщика.

Модель: `model-check-plugin/engine/testdata/promela/starvation.pml`

---

## 1. Почему нет: контрпример

```promela
bit done;

active proctype A() { bit t; do :: t = 1 - t od }   /* бесконечный цикл */
active proctype B() { done = 1 }                     /* один-единственный шаг */
```

Семантика Promela — это **произвольное чередование** (arbitrary interleaving): на каждом шаге планировщик выбирает *любой* разрешённый переход. Никакого обещания, что каждый процесс когда-нибудь получит ход, в язык не встроено.

Оператор `t = 1 - t` в `A` разрешён всегда, и `A` никогда не завершается. Значит, существует законная бесконечная трасса

```
A: t=1 → A: t=0 → A: t=1 → A: t=0 → …
```

в которой `B` навсегда остаётся на своей начальной метке (строка 17) и `done` навсегда равно 0. Это и есть **голодание (starvation)** процесса B: он *разрешён* на каждом шаге, но ни разу не *выбран*.

Обратите внимание на важную деталь: это **не дедлок**. Проверка на дедлок (invalid end state) проходит успешно — система всегда может сделать шаг, просто этот шаг всегда делает не тот процесс. Поэтому обычный прогон `spin -a` без флага `-a` (поиск циклов принятия) ничего не находит; нужна именно проверка живости.

## 2. Машинная проверка

Проверялось свойство `<> done` («рано или поздно `done` станет истинным»).

### SPIN 6.5.2 (эталон)

```
$ spin -a starvation.pml && gcc -O2 -DNOREDUCE -o pan pan.c

$ ./pan -a            # справедливость выключена
pan:1: acceptance cycle (at depth 0)
... errors: 1                                   ← СВОЙСТВО НАРУШЕНО

$ ./pan -a -f         # включена слабая справедливость
... errors: 0                                   ← СВОЙСТВО ВЫПОЛНЕНО
```

Трасса контрпримера (`spin -t -p -g`):

```
  <<<<<START OF CYCLE>>>>>
Never claim moves to line 4     [(!(done))]
  2:  proc 0 (A:1) starvation.pml:11 (state 1)  [t = (1-t)]
  4:  proc 0 (A:1) starvation.pml:11 (state 1)  [t = (1-t)]
...
        done = 0
  4:  proc 1 (B:1) starvation.pml:17 (state 1)  ← B так и стоит на своём единственном операторе
```

Цикл длины 2 (`t: 0→1→0`), внутри которого `done == 0`; процесс B заморожен.

### Движок репозитория `mcd` (v0.1.0) — независимое подтверждение

```
$ mcd check --promela …/starvation.pml --ltl '<> done' --fairness none
  deadlock → verified
  ltl1     → violated      (цикл: 4 шага, начиная с шага 3; final: done = 0)

$ mcd check --promela …/starvation.pml --ltl '<> done' --fairness weak
  deadlock → verified
  ltl1     → verified
```

Оба инструмента дают одинаковый вердикт. Поиск в обоих случаях полный (`"stop": "complete"`, `"complete": true`), так что «нарушено» — это доказанный факт, а не исчерпание бюджета.

Сырые выводы сохранены рядом: `spin-runs.txt`, `mcd-fairness-none.json`, `mcd-fairness-weak.json`, `starvation-with-ltl.pml`.

## 3. Когда утверждение всё-таки верно

При **слабой справедливости** свойство выполняется, и слабой достаточно — сильная не нужна. Слабая справедливость требует: если процесс *непрерывно* разрешён начиная с некоторого момента, он рано или поздно сделает шаг. Оператор `done = 1` — это присваивание, а присваивание в Promela разрешено всегда и безусловно. Значит, B непрерывно разрешён с момента старта, слабая справедливость обязывает его сработать, и `done` становится 1.

(Сильная справедливость — «процесс, разрешённый бесконечно часто, рано или поздно сработает» — здесь тоже сработала бы, но она строго сильнее и не требуется. В `mcd` она, судя по справке, и не реализована: `strong is not executed, FR-008`.)

Заметим ещё, что `done` нигде не сбрасывается, поэтому в этой модели `<> done` эквивалентно `<>[] done`: раз выставленный флаг держится навсегда.

## 4. Что это значит практически

Ответ зависит от того, что вы моделируете:

- **Если `A` и `B` — потоки ОС на вытесняющем планировщике**, то на практике B почти наверняка отработает: реальные планировщики (Linux CFS, Windows) дают по меньшей мере слабую справедливость. Тогда верификацию надо вести с `pan -a -f` / `--fairness weak`, и свойство держится.
- **Если `A` и `B` — кооперативные задачи, обработчики в одном event-loop, или процессы на распределённом арбитре без гарантий**, то контрпример выше — это реальный сценарий зависания, а не артефакт модели. Нечестная семантика SPIN здесь честнее.

Поэтому корректная формулировка вердикта такая: **сама модель не гарантирует, что `done` будет выставлено; гарантию даёт только внешнее предположение о справедливости планировщика, и его надо задавать явно.** Если в вашей системе такой гарантии нет, `B` может голодать бесконечно.

---

### Явно помеченные допущения

- **Допущение 1.** Вопрос истолкован как свойство живости `<> done` («рано или поздно `done` станет 1»), поскольку именно это подразумевает формулировка «рано или поздно выставит». В файле нет объявленной LTL-формулы, она добавлена для проверки.
- **Допущение 2.** Комментарий в шапке файла (строки 1–5) описывает ровно это поведение, но вердикт выше получен независимой машинной проверкой, а не пересказом комментария; результаты совпали с комментарием.
- **Допущение 3.** «Обязан» понимается как «во всех допустимых исполнениях», а не «в типичном». Если имелось в виду «в большинстве прогонов симуляции» — то да, `spin` в режиме симуляции с случайным выбором почти наверняка выполнит B; но верификация говорит о всех трассах, и среди них есть плохая.
