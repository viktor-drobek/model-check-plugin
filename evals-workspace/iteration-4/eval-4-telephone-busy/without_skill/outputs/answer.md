# Может ли телефон зависнуть в состоянии Busy?

**Модель:** `Promela - examples/CH14/version1` (Fig. 13.4 / 13.5 — коммутатор, только исходящие вызовы)

## Короткий ответ

**Нет, не может.** Ни один из процессов не способен остаться в состоянии `Busy` навсегда.
Проверено исчерпывающим перебором в Spin 6.5.2 — полное пространство состояний модели
составляет всего 9 состояний, ошибок нет.

## Что именно проверялось

В модели два разных метки `Busy` — у абонента (`subscriber`) и у коммутатора (`switch`).
Вопрос «телефон завис в Busy» на практике означает состояние с гудком «занято»
(`switch:Busy`, куда ведут все ветки `busytone`), поэтому проверены **обе** метки.

Формулировка свойства на LTL:

```promela
#define sw_busy  (switch[1]@Busy)
ltl no_hang_sw  { [] (sw_busy -> <> !sw_busy) }     /* всякий заход в Busy когда-нибудь заканчивается */

#define sub_busy (subscriber[0]@Busy)
ltl no_hang_sub { [] (sub_busy -> <> !sub_busy) }
```

Сама модель при этом не менялась — добавлены только `#define` и `ltl`-объявления
(они не порождают переходов и не влияют на поведение).

## Результаты прогонов

| # | Проверка | Команда | Результат |
|---|----------|---------|-----------|
| 1 | Тупики / недопустимые конечные состояния | `pan -DSAFETY -m10000` | **errors: 0**, 9 состояний, глубина 11 |
| 2 | `[] (switch[1]@Busy -> <> !switch[1]@Busy)` | `pan -a` (acceptance cycles, fairness **выключена**) | **errors: 0** |
| 3 | `[] (subscriber[0]@Busy -> <> !subscriber[0]@Busy)` | `pan -a` | **errors: 0** |
| 4 | Контроль на вакуумность: `[] !switch[1]@Busy` | `pan -a` | **errors: 1** (ожидаемо) |

Прогон 4 — обязательный контроль: он показывает, что состояние `Busy` вообще
**достижимо**, то есть прогоны 2 и 3 не проходят «вхолостую» на недостижимой посылке.
Полный лог и трасса-свидетель — в `spin-run/verification.log`.

Важно, что прогоны 2–3 сделаны **без** флага `-f` (слабая справедливость отключена):
Spin искал любые циклы, в том числе «несправедливые». Их нет — значит, свойство
держится безусловно, без всяких предположений о планировщике.

Отдельно отмечу методическую деталь: при наличии never claim Spin **отключает**
проверку недопустимых конечных состояний (`invalid end states - (disabled by never claim)`),
поэтому тупик в `Busy` прогонами 2–3 сам по себе пойман бы не был. Его закрывает
прогон 1, где эта проверка включена и ошибок нет. Только совокупность
«прогон 1 + прогоны 2–3» даёт полный ответ: ни тупика в `Busy`, ни бесконечного
цикла внутри `Busy`.

## Почему так — механизм

Ключ в том, что канал объявлен как **рандеву**: `chan tpc = [0] of { mtype }`.
Отправка без готового получателя не выполняется, а просто блокируется.

Коммутатор в `Busy` имеет единственный оператор:

```promela
Busy:	tpc?onhook -> printf("MSC: notone\n"); goto Idle
```

Абонент в это время стоит на своей метке `Busy` и предлагает две альтернативы:

```promela
Busy:	if
	:: tpc!digits -> goto Busy
	:: tpc!onhook -> goto Idle
	fi
```

Ветка `tpc!digits` **не исполнима**: коммутатор в `Busy` принимает только `onhook`,
а рандеву требует совпадения сообщения. Spin выбирает недетерминированно только
среди *исполнимых* веток, поэтому у системы в этой конфигурации есть ровно один
возможный переход — рандеву `onhook`. Он и совершается, после чего коммутатор
печатает `notone` и уходит в `Idle`, а абонент — на метку `Idle`.

То есть «зависнуть» тут нечему:

* **тупика нет** — переход всегда есть (прогон 1);
* **живого зацикливания нет** — альтернатива «жать цифры бесконечно» физически
  заблокирована, повторный `digits` возможен только пока коммутатор стоит в `Dial`,
  а туда он попадает лишь после нового `offhook` (прогоны 2–3).

Достижимый цикл модели целиком укладывается в одну схему:

```
Idle --offhook--> Dial --digits--> Wait --+--busytone--> Busy --onhook--> Idle
                   |                      |
                   +--onhook--> Idle      +--ringtone--> Connect --busytone/notone--> Busy --onhook--> Idle
```

Все стрелки из `Busy` ведут обратно в `Idle`, других выходов и петель нет.

## Оговорки и допущения

* **Допущение (вопрос уточнить было не у кого):** под «состоянием Busy» понимается
  метка `Busy` в Promela-коде. Проверены обе такие метки — и в `switch`, и в
  `subscriber`, так что трактовка вопроса на результат не влияет: ответ «нет» в обоих
  случаях.
* Ответ относится **только к `version1`** — это заведомо упрощённая модель:
  один абонент, только исходящие вызовы, нет удалённого отбоя (см. комментарий
  `/* no remote hang up */` в коде). В последующих версиях (`version2`…`version6`)
  модель богаче, и там результат может быть иным; в частности, рядом лежит готовый
  `version3.trail` — признак того, что для `version3` контрпример был найден.
* LTL-свойство `[] (Busy -> <> !Busy)` соответствует CTL-формуле `AG(Busy -> AF !Busy)`.
  Она строго сильнее, чем `AG(Busy -> EF !Busy)` («из Busy *можно* выйти»), так что
  и более слабая формулировка вопроса выполняется автоматически.

## Как воспроизвести

```bash
cd "Promela - examples/CH14"
cp version1 /tmp/version1.pml && cd /tmp

# 1) тупики
spin -a version1.pml && gcc -O2 -DSAFETY -o pan pan.c && ./pan -m10000

# 2) зависание в Busy (файл sw_busy.pml = version1 + ltl, см. spin-run/)
spin -a sw_busy.pml && gcc -O2 -o pan pan.c && ./pan -a -m10000
```

## Артефакты

Всё лежит в `spin-run/` рядом с этим файлом:

* `version1.pml` — исходная модель (копия `CH14/version1`)
* `sw_busy.pml` — модель + LTL `no_hang_sw` (коммутатор)
* `sub_busy.pml` — модель + LTL `no_hang_sub` (абонент)
* `reach.pml` — контроль на вакуумность `[] !sw_busy` + трасса-свидетель
* `verification.log` — полный вывод всех четырёх прогонов pan
