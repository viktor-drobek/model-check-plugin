# Проверка модели `Promela - examples/CH17/simple1.pr`

**Итог: верификация падает — `assertion violated (x==6)`. Но это не ошибка логики модели, а ошибка самой модели как объекта верификации: состояние C-переменной `x` не отслеживается Spin'ом, поэтому поиск в пространстве состояний работает на испорченных данных.**

---

## 1. Модель

Файл: `${REPO_ROOT}/Promela - examples/CH17/simple1.pr`

```promela
c_code { int x; }

active proctype simple()
{
   c_code { x = 2; };
   if
   :: c_code { x = x+2; }; assert(c_expr { x==4 })
   :: c_code { x = x*3; }; assert(c_expr { x==6 })
   fi
}
```

Инструмент: Spin Version 6.5.2 (6 December 2019), gcc, Linux.
Команды: `spin -a simple1.pr && gcc -O2 -o pan pan.c && ./pan -m10000`.

## 2. Результат верификации

Синтаксис корректен (`spin -a` завершается без ошибок и предупреждений).

```
pan:1: assertion violated ( x==6 ) (at depth 2)
pan: wrote simple1.pr.trail

Full statespace search for:
	never claim         	- (none specified)
	assertion violations	+
	acceptance   cycles 	- (not selected)
	invalid end states	+

State-vector 12 byte, depth reached 4, errors: 1
        6 states, stored
        0 states, matched
```

(`Warning: Search not completed` здесь означает только то, что поиск прерван на первой найденной ошибке.)

Полный лог: `logs/01-pan-simple1.log`.

## 3. Почему это ложное срабатывание по содержанию и настоящая ошибка по сути

Контрпример, выданный верификатором, при воспроизведении выглядит **невозможным**:

```
  1:	proc  0 (simple) simple1.pr:5 (state 1)	[ x = 2; ]
  2:	proc  0 (simple) simple1.pr:7 (state 6)	[ x = x*3; ]
  3:	proc  0 (simple) simple1.pr:8 (state 5)	[assert( x==6 )]
```

По трассе `x = 2`, затем `x = 2*3 = 6`, и `assert(x==6)` обязан выполниться. То есть трасса сама себе противоречит — верный признак того, что сломано не свойство, а учёт состояния.

Важная деталь: `spin -t -p` для такой модели вообще не годится и честно об этом предупреждает — фрагменты `c_code` при симуляции не исполняются, а только печатаются. Корректное воспроизведение — только `./pan -r` (`logs/02-pan-replay-trail.log`).

### Причина

`int x` объявлена внутри `c_code { ... }`, то есть это обычная глобальная переменная C в сгенерированном `pan.c`. Она **не входит в вектор состояния** (`State-vector 12 byte` — там только состояние процесса, без `x`). Поиск в Spin — это DFS с откатами: при возврате из ветки верификатор восстанавливает свой вектор состояния, но про `x` он ничего не знает и восстановить её не может.

Отсюда фактический сценарий поиска:

1. `x = 2`;
2. первая ветка: `x = x+2` → `x = 4`, `assert(x==4)` проходит;
3. откат к точке ветвления — **`x` остаётся равной 4**, а не возвращается к 2;
4. вторая ветка: `x = x*3` → `x = 12`;
5. `assert(x==6)` падает.

### Подтверждение эксперментом

Я добавил `printf` внутрь каждого `c_code` и повторил поиск (`repro/simple1-instrumented.pr`, `logs/03-pan-instrumented.log`):

```
[search] init      x=2
[search] branch1   x=4
[search] branch2   x=12      <-- ожидалось 6
pan:1: assertion violated ( x==6 ) (at depth 2)
```

Значение `12 = 4*3` прямо показывает утечку состояния между ветками.

## 4. Исправление

Достаточно объявить `x` отслеживаемой:

```promela
c_code { int x; }
c_track "&x" "sizeof(int)";
...
```

Результат (`repro/simple1-with-c_track.pr`, `logs/04-pan-c_track-fixed.log`):

```
[search] init      x=2
[search] branch1   x=4
[search] branch2   x=6       <-- теперь корректно
...
State-vector 20 byte, depth reached 4, errors: 0
        8 states, stored
```

Вектор состояния вырос с 12 до 20 байт (в него вошла `x`), число состояний с 6 до 8 (ветки перестали склеиваться), ошибок — ноль.

## 5. Это ровно тот урок, ради которого пример написан

В той же директории лежит `simple2.pr` — та же модель, но уже с `c_track "&x" "sizeof(int)"`. Пара `simple1.pr` / `simple2.pr` из главы 17 («Embedded C Code») — это демонстрация «до/после»: `simple1.pr` **должен** падать, показывая, что неотслеживаемое C-состояние ломает верификацию.

Проверка `simple2.pr` как есть (`logs/05-pan-simple2-book-fix.log`):

```
State-vector 20 byte, depth reached 4, errors: 0
        8 states, stored
```

**Предположение (явно помечено):** пользователь просил проверить именно `simple1.pr` и не указывал, нужно ли его чинить. Я исходил из того, что требуется диагноз, а не правка, поэтому **исходный файл в репозитории не изменялся**; исправленный вариант сохранён отдельно в `outputs/repro/`.

## 6. Практические выводы

1. Любое C-состояние, которое влияет на переходы или на проверяемые свойства, обязано попасть в вектор состояния — через `c_track "&var" "sizeof(...)"` либо через `c_state "T v" "Global"` с доступом как `now.v` (последний приём используется в `example1` из той же директории).
2. Без этого Spin даёт не просто неполную, а **неверную** верификацию: и ложные срабатывания (как здесь), и — что опаснее — ложные «прохождения», потому что склеивание состояний по неполному вектору может скрыть реальные ошибки.
3. Для моделей с `c_code` контрпримеры воспроизводить только через `./pan -r`, никогда через `spin -t`.
4. Диагностический признак «сломанного состояния»: трасса, которая при ручной проверке не может привести к нарушению свойства.
