# Расшифровка контрпримеров ожидания

Источник: `liveness-none.report.json` и `liveness-weak.report.json`. Это расшифровка записанных движком трасс, а не отдельное воспроизведение. Шаги `never:ltl1/2` принадлежат автомату отрицания свойства и опущены ниже. Шаги `-` в трассах с `weak` — служебный учёт справедливости; действий клиентов или сервера они не обозначают.

## `ltl2`: клиент 1 ожидает бесконечно, `fairness: none`

Формула: `[] (waiting1 -> <> working1)`. После шага 8 `waiting1 = true`: клиент 1 хочет послать запрос. К этому времени сервер уже принял запрос клиента 0 (шаг 4), выдал ему разрешение (шаг 10), а после работы получил освобождение (шаг 20). На шаге 24 сервер **снова выбирает запрос клиента 0**, хотя клиент 1 тоже пытается передать запрос. Это первый причинный выбор, позволяющий продолжить ожидание клиента 1.

Префикс трассы заканчивается шагом 26 (`accepted0 = true`). Цикл — шаги 27–44, повторяющиеся бесконечно:

| Шаг | Действие модели | Смысл |
|---:|---|---|
| 28 | `grant0!1` / `grant0?1` | Клиент 0 получает разрешение. |
| 30, 32 | `accepted0 = false`, `waiting0 = false` | Он покидает ожидание. |
| 34, 36 | `working0 = true`, затем `false` | Он работает и заканчивает. |
| 38 | `release!0` / `release?0` | Сервер получает освобождение. |
| 40 | `waiting0 = true` | Клиент 0 начинает следующую попытку. |
| 42 | `request!0` / `request?0` | Сервер опять принимает запрос клиента 0. |
| 44 | `accepted0 = true` | Запрос клиента 0 помечен принятым. |

Весь цикл `waiting1 = true`, `accepted1 = false`, `working1 = false`. Запрос клиента 1 так и не передаётся серверу. Глобального тупика здесь нет: клиент 0 и сервер продолжают работу. Класс причины: описанный протокол допускает голодание при недетерминированном выборе запросов; это не свидетельство о конкретной реализации, которой нет.

## `ltl1`: симметричное ожидание клиента 0, `fairness: none`

Формула: `[] (waiting0 -> <> working0)`. После первой успешной работы клиент 0 снова ставит `waiting0 = true` (шаг 22). Сервер выбирает запрос клиента 1 (шаг 24), затем клиент 1 работает и освобождает сервер (шаг 38). Цикл — шаги 39–56: клиент 1 вновь ставит `waiting1 = true`, передаёт запрос, получает разрешение, работает и освобождает сервер. Эти шаги повторяются бесконечно; `waiting0 = true`, `accepted0 = false`, `working0 = false` на всём цикле. Первый причинный выбор для бесконечного ожидания — принятие сервером запроса клиента 1 на шаге 24 при уже ожидающем клиенте 0, а затем повторное принятие на шаге 42.

## Проверка с `fairness: weak`

`ltl1` и `ltl2` снова получили `violated` / `exhaustive`: циклы начинаются с шагов 42 и 29 соответственно. В системной проекции тех трасс сервер многократно обслуживает одного клиента, пока второй ждёт возможности синхронно передать запрос. Передача второго клиента доступна лишь в моменты, когда сервер снова принимает запросы, а не непрерывно. Поэтому слабая справедливость выбора **процессов** не исключает этот цикл. Это отдельный анализ чувствительности; пользователь не подтверждал справедливость планировщика.
