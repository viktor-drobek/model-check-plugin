# Fix: `--fairness weak` reported cycles that SPIN does not (confirmation)

Branch `fix/weak-fairness-null-steps`, from `738627b` (the published 0.2.0). The version,
`engine/bin`, `SHA256SUMS` and `BUILD-INFO.json` are untouched.

Two rounds. The first (`cb85740` .. `5ee46f5`, sections 1-8) removed the null-step cycles.
A review of it (three blind reviewers and an orchestrator who ran models, the engine and
SPIN) and a decision study with an independent checker followed; the second round
(`90d88fd` onwards, section 11) applies their findings and decisions, and found four more
defects on the way. Sections 6, 9 and 10 were brought up to date; sections 1-5, 7 and 8
are the record of the first round as it was written (their counts are those of the code
at `5ee46f5`).

## 1. What was wrong

With `--fairness weak` the engine reported a violation whose loop consisted of
weak-fairness null steps (process `-`) and nothing else, on a state in which every
process is blocked, where `pan -a -f` / `pan -l -f` report no error. Without fairness the
same models agreed with pan. Found by the differential run of the cross-review of the
cycle-lasso fix (not part of that diff; identical on 0.2.0): 16 of 379 SPIN-valid
weak-fairness rows disagreed, all as "engine violated / pan no error" (11 `--progress`,
3 never claims, 2 accept labels), none in the other direction, and none without fairness.

Reproductions, under `engine/testdata/promela/` (each runs in milliseconds):

| file | what it is | engine 0.2.0, `--fairness weak` | pan 6.5.2 |
|---|---|---|---|
| `weakfair-claim-m5271.pml` | never claim on accept locations over two bits and a byte, one process with an atomic loop that blocks (generated model m5271) | `never` violated, loop of 3 null steps | `-a -f`: 0 errors |
| `weakfair-progress-r1.pml` | three processes with progress labels, all blocked, P0 at `progress_0_0` (generated model r1), `--progress` | `progress` violated, loop of 5 null steps | `-l -f`: 0 errors |
| `weakfair-claim-blocked.pml` | the smallest shape of the first: `a = 1; a == 0` and a claim whose only edge needs `a == 0` | violated, loop of 3 null steps | 0 errors |
| `weakfair-np-claim.pml` | the smallest shape of the second: P blocks at its progress label | violated | 0 errors |
| `weakfair-np-deadlock.pml` | P blocks for good after its progress label, `np_` true | violated | 0 errors |

Two more models are in the suite to hold the other direction (section 6):
`weakfair-stutter-accept.pml` (a blocked system, a claim that loops on `accept_S0`: pan
and engine both report the cycle) and `weakfair-stutter-cycle.pml` (a blocked system, a
claim alternating between an accepting and a non-accepting location).

## 2. What SPIN's weak-fairness construction does (evidence)

Read from `pan.c` generated by SPIN 6.5.2 (`spin -a`; the `-DVERBOSE` traces below are
the program's own account) and checked by runs; a model that blocks all processes is the
place where the constructions can differ, so that is where the evidence is.

* **No separate counting step.** `pan -f` carries the A-bit and a counter `_cnt` in the
  state (Holzmann's "fairness rules"): Rule 1 sets the bit and `cnt = nr_pr + 1` in an
  accepting state; Rule 2 decrements `cnt` while the loop over the processes visits the
  process that `cnt` waits for, whether that process executes or has no executable
  transition (a blocked process "counts" by the restart of the loop with the decrement
  kept, `II = INI_P`); Rule 3 clears the bit when `cnt == 1`. All three happen *inside*
  the steps of the product. A cycle is reported when a *real step* leads back to the seed
  state with `cnt == 1` (`pan.c`, `AllOver`: `if (fairness && now._cnt[1] != 1) /* treat
  as new state */`).
* **The claim moves at every step; a blocked claim ends the path.** In `-DVERI` mode the
  frame that must make a claim move (`tau&4`) tries process 0 only; with no executable
  claim transition the frame has no successor. The "fairness default move" that pan adds
  when no process can move (`pan.c`, "fairness default move (all procs block)") is guarded
  by `fairness && _n == 0 && !(trpt->tau&4) /* in program move */ && cnt > 0`: it exists
  only in a program frame, after the claim has moved, and the next frame is a claim frame
  again. So the default move is itself a step of the product.
  Run on `weakfair-claim-blocked.pml` (`pan -DVERBOSE -a -f`): Rule 1, Rule 2, then
  `Down - claim accepting` at the blocked claim, and no default move: the path ends,
  0 errors. Run on `weakfair-stutter-accept.pml`: Rule 1, Rule 2, `fairness default move
  (all procs block)`, `Down - claim accepting`, Rule 3, again, then the cycle: 1 error.
* **No default move, and no stutter, under `-DNP`.** The default move is inside
  `#ifndef NP`, and `pan -l` has no stutter extension, so a state in which nothing can
  move has no successor in the non-progress product. Run on `weakfair-np-deadlock.pml`
  (`-DNP -DVERBOSE -l -f`): Rule 1, Rule 2, undo, and no default move; 0 errors. This is
  the rule the engine already followed without fairness (`noStutter`, K3,
  `steps/k3-mutation-report.md`) and documents in `counterexamples.md` §2a.
* **`-f` and the stutter extension.** SPIN 6.5.2's `pan.c` has `if (!(trpt->tau&4) &&
  !fairness) /* 9/2025 added !fairness */` in front of the claim's stutter step: under `-f`
  the claim's own stutter step is off, and only the default move above remains.

## 3. The cause in the engine

`explore/cycle.go` implemented the n + 2 copies as a counter in the product state, `k`
in 0..n+1, advanced by *null steps* (a product move that leaves the system state and
the claim location unchanged) as well as by moves, and closed the round with a null step
from copy n + 1 back to copy 0. A null step is not a step of the product: the claim has
not moved and no system move was made. So whenever an accepting product state `(s, q)`
has every process blocked, the copies form the cycle
`(s,q,0) -> (s,q,1) -> ... -> (s,q,n+1) -> (s,q,0)` of null steps and nothing else, through
an accepting state. The nested DFS found it and reported an acceptance (or non-progress)
cycle. That is no run of anything:

* if the claim has no enabled edge in `s` (a blocked claim, or `np_` false because a
  process sits on a progress label), pan's path ends there (section 2);
* under `--progress`, a blocked state has no successor at all in pan's product, and the
  engine's own `noStutter` rule says so without fairness; with fairness the null cycle
  put the deadlock back as a "non-progress cycle", the exact conflation K3 had removed.

It is a defect, not a design choice: the documented intent is "as `pan -f`"
(`features/g4-ltl.feature`, `fairness.md` §2), the feature vocabulary says that a claim
without an enabled edge prunes the path, and `counterexamples.md` says that a `progress`
loop is a real cycle of the model. The null step was introduced as bookkeeping and the
cycle made of bookkeeping alone was never considered; the weak-fairness item of
`steps/g4-confirmation.md` compared 11 weak rows with pan, and those did not expose it.

## 4. The fix (`cb85740`)

Copy n + 1 has no null step. The next step of the product, whatever it is (a claim step
and a system move, or a stutter step), leads from copy n + 1 to copy 0 (`apply`; in
`nextProduct` the case disappears). Every other rule is unchanged.

Why this is right, not only why the repros pass:

* *Sound.* Every cycle of the product through copy 0 passes through copy n + 1 and leaves
  it by a step of the product, so the cycle contains a step of the product; with the null
  steps removed it is a closed walk of the claim x system graph through an accepting state
  (a run), and in every round each process either moved or was blocked in a stored state
  (the null steps' guard), which is weak fairness. A loop made of null steps alone cannot
  exist.
* *Complete.* A weakly fair accepting run has a lifting: a round starts at an accepting
  state in copy 0 (null step to copy 1); for each copy k the run either moves process
  k - 1 (copy k + 1), or meets a stored state where it is blocked (null step), or, if it
  is enabled from some point on, must move it infinitely often; when copy n + 1 is reached
  the next step of the run is a step of the product and returns to copy 0. The run has
  infinitely many accepting states, so rounds restart infinitely often. The only thing the
  change delays is the start of the next round by one step, which loses no run.
* *Same as pan.* pan counts blocked processes inside the steps, never in a step of their
  own, and closes the round by a real step to the seed (section 2).

Counterexamples change in one visible way: the note "copy n + 1 -> 0, every process has
moved or been blocked once" is gone (there is no such step); the real step that closes a
round carries no note. The `reason` of a weak-fairness `violated` and its trace shape are
otherwise as before, and a loop now always contains a claim step or a process move or a
stutter step (`weakfair_test.go`, scenario "contains a step that is not a weak-fairness
null step").

## 10. Decisions

Settled by the decision study (`testdata/weakdecision`, `fairness.md` §6b) and applied in
the second round (§11). The rule behind all of them: ground truth is the textbook definition
of weak fairness under the stutter-extension convention; conformity with `pan -f` is
secondary; a missed violation (a wrong `verified`) is worse than a false `violated`.

1. **Stutter extension under weak fairness (D1): keep.** A stopped system with a claim that
   goes on moving is a weakly fair run. The natural example is `<>[]p` on a system that
   blocks at once with p false: weakly fair (nothing is enabled), p false for ever, so
   `<>[]p` is violated. `pan -a` finds it (3 errors), `pan -a -f` does not (0): pan 6.5.2
   switched the claim's stutter step off under `-f`, so a weakly fair counterexample
   vanishes under the fairness assumption. Following pan would make `<>[]p` on a deadlocked
   system `verified` under `weak` and `violated` under `none`. Documented divergence
   (`fairness.md` §6b item 1; the scenario "documented divergence from pan -f").
2. **`provided` false is blocked (D2): keep, documented harder.** The engine counts such a
   process as blocked (it is not enabled). pan's `-f` can miss the resulting violation, and
   the miss depends on the order of the processes (`d2_pf_a` is missed, `d2_pf_b`, the same
   model with the processes swapped, is found): a false negative of pan, not "pan is
   stricter". The decision is consistent only because §11.1 made the moves honour
   `provided` on both sides of a rendezvous.
3. **`timeout` (D3): the engine changed** (`431bc01`). Before the change the divergence was
   only false violations (`blocked` marked timeout-only processes disabled everywhere).
   The reconciliation of the cross-review's `to1` and `to2` that had to come first is in
   §11.3: they are weakly fair accepting cycles by the definition, and pan and the engine
   said so; only the oracle, through a defect of `Stepper.Enabled`, said otherwise. The

   `pan -a -f` and `pan -l -f` have it.
4. **pan's accept stutter (C5): keep.** `m31278` and its reduction `c5_min3`: no stuttering
   run is accepting and every accepting cycle is unfair, so `verified`; pan reports an

   `spin -a -o1 -o2 -o3`). So "engine verified, pan error" is not impossible; it was 0 on the

5. **The atomic holder (C1): `hasEnabled` is left as it is; the cause was in the frontend**
   (§11.2). Documented gap: an atomic loop that never gives up the control is
   `inconclusive`.
6. **The excluded models** wait for `fix/cycle-lasso-panic` (§9).
7. **Version and release notes.** Not bumped. A published 0.2.0 answers `--fairness weak`

## 11. Second round: the review's findings and the decisions of the study

Rule for every decision below: ground truth is the textbook definition of weak fairness under
the stutter-extension convention; conformity with `pan -f` is secondary; a missed violation
(a wrong `verified`) is worse than a false `violated`. Every item was done test first: a
scenario or test shown failing for the stated reason, then the smallest fix at the cause,
then green, one commit per item. Commits, in order: `90d88fd` (11.1), `d20b6cb` and `5d4a1d3`
(11.2), `90deed4` and `431bc01` (11.3), `431bd00` (11.4), `c1de020` and `44d8bae` (11.5),
`e208caf` (11.9), `ed60989` and this record's commit (docs).

### 11.1 `provided` on both sides of a rendezvous (review finding 2)

`provided` gates every transition of a process (`enabled()` says so), but `nextEnabled` took
the rendezvous branch for a send without asking the sender's clause, and `rvMatch` did not
ask the receiver's. A process kept from moving by `provided` took part in handshakes it
must not. The review had found the sending side (`provided-rv-send.pml`: `P provided (b == 1)
{ ch!1 }`, `Q { ch?x; assert(x == 0) }`: pan finds the invalid end state and no assertion
violation, 1 state; the engine said `deadlock` verified and `assert` violated, 4 states) and
reported the receiving side as correct. **It was not**: the verdicts of the review's
`prov_rv2` happened to coincide with pan's, but its counterexample showed the receiver with
a false clause taking the handshake, and `provided-rv-recv.pml` (`Q { ch!1; assert(false) }`)
makes the difference visible (engine: `assert` violated, pan: no error). Both sides now ask
`providedHolds`. Red: the two scenarios of `g1-promela.feature` and
`TestProvidedGatesBothSidesOfARendezvous`.

*Default-search results that change.* Over the 236 pre-existing models (the 158 corpus
files of §7, the 34 `testdata/promela` and the 44 `testdata/weakfair` models) x 11 command
lines: none changes because of this (the models with `provided` and a rendezvous channel
among them are `m5228` and `m5322`); the only changes are the two new models. On 3,000
generated models (the 2 x 1,000 of §6 and 1,000 of the new generator, 100 of them with
`provided` and a rendezvous channel) this commit alone changes the default search of 5
models, in their state counters only: no property of any of them changes its status.

### 11.2 `hasEnabled` and the exclusive holder (study finding C1): not the cause

The study's `new_atomic_hold.pml` (`P { atomic { do :: x = 1 - x od } }`, `Q { y = 1 }`, a
claim accepting while y == 0) was answered `verified` under weak fairness; by the definition
P keeps the lock for ever, Q is not executable, so the run is weakly fair and accepted:
`violated`. The study's diagnosis was that `hasEnabled` ignores the exclusive holder. **That
cannot produce the wrong verdict**: the product stores no state in which a holder has an
enabled move (such a state is an intermediate atomic state and is never stored), and the
copies are judged at stored states only, so `hasEnabled` never sees a non-holder next to an
enabled holder. A holder-aware `hasEnabled` would also remove the "enabled throughout the
loop" note for loops that contain intermediate states. It is left as it is. (The note
cannot be exercised on this branch for such loops: they hit the unmerged lasso defect.)

The real cause was in the Promela frontend: an edge is atomic when its target lies inside
the block, and the head of a `do` that is the first statement of an `atomic { }` block is the
location in front of it, which is outside. So `atomic { do :: x = 1 - x od }` was lowered as
plain steps (Q enabled everywhere, the cycle unfair, `verified`). The same defect gave
false violations in the default search, with no fairness at all: `atomic { do :: n < 3 ->
n++ :: else -> break od }` with `Q { assert(n == 0 || n == 3) }`: pan finds no error (7
states), the engine reported the assertion violation (16 states); `d_step { do ... od }` the
same. The fix (`d20b6cb`): the edges that close an iteration of a loop inside an
atomic / d_step block keep the control (the `break` of the loop does not). When the loop's
head is also the start of another alternative (the block is one option of an outer
`if`/`do`) a lock bit cannot keep the other alternative out of the block, and pan needs a
state of its own for the inside: the frontend now **refuses** that shape (`outside-subset`);
node splitting (duplicating the options of the loop for the first iteration) would lower it
exactly but changes the location structure that the state counts of the corpus rest on, and
was not attempted. Over the 416 model files of the repository and the corpus the IR of every
existing model is byte-identical; only the three new test models differ (and the repository
has no model with such a shape: `CH18/tpc6` has one and is rejected earlier for an
unrelated construct).

After the fix an atomic loop that never gives up the control is `inconclusive` (bounded):
the engine stores no state inside an atomic sequence, so there is none to close a cycle on,
and pan cannot answer either (its search is truncated). With the default budgets that is
the depth budget (1,000,000 steps, about 2 s and 0.5 GB). The study's definition-based verdict
(`violated`) is therefore **not reached**; the scenario asserts the honest answer, and
`new_atomic_split` (atomic blocks that end: correctly `verified`) and `d3_at` are held back
until `fix/cycle-lasso-panic` is merged. Before: `violated` without fairness (for the wrong
reason) and `verified` with weak fairness; after: `inconclusive` for both.

### 11.3 `timeout`: the reconciliation of to1 and to2, and decision D3

*Reconciliation first.* The review reported `to1.pml` and `to2.pml` (`do :: timeout -> ...`
loops with a claim accepting while b == 0) as "engine weak violated, `pan -a -f` 1 error,
oracle: no fair cycle", which contradicted the study (pan follows the definition). Hand
graphs (`testdata/weakdecision/graphs/to1.txt`, `to2.txt`, made by `wfcheck.py`, which now
encodes both; to1 is the study's `d3_ctl_split`): in both, the cycle through P's own
steps passes through states where P's second statement is executable, so `timeout` is false
there and Q is disabled; Q is disabled infinitely often, the cycle is weakly fair, the claim
stays accepting: **violated**. `pan -a -f`: 1 error each; the engine: violated. Engine, pan
and the definition agree; **the oracle was wrong**: its graph comes from `Stepper.Enabled`,
which enumerated moves with a frame whose `enabled` counter stayed at zero, so the timeout
phase ran in every state and P2's timeout was listed next to P1's ordinary move. That is a
defect of the Stepper itself: `mc_simulate` offered timeout moves in states where another
process could move, and `Apply` accepted them. Fixed (`90deed4`; red: a unit test and a
g2 scenario); the oracle then says a fair cycle exists on to1 and to2 and none on `d3_one`.

*D3.* `blocked(p)` used `hasEnabled`, which evaluates with `timeout = false`, so a process
whose next statement is a bare `timeout` was blocked in every state, timeout states
included: a loop made of timeout states only, in which such a process never moves, looked
weakly fair. `d3_one.pml` (`P: do :: timeout od`, `Q: timeout -> b = 1`, a claim accepting
while b == 0): the engine said `violated`; the definition, `pan -a -f` and `pan -l -f` (on
`d3_np`) say no cycle. Only false violations. `search.executable` (an ordinary enabled edge,
or, in a timeout state, an enabled `timeout` edge) now decides `blocked` and the note of a
loop found without fairness (`431bc01`). Red: four rows of the new scenario outline, four
rows of the pan differential outline (`engine violated | pan verified | DISAGREE`),
`TestWeakFairnessTimeoutOwesAMove`. The controls `d3_ctl_split`, `d3_ctl_skip`,
`d3_two_loop`, `d3_mixed`, `d3_np_flip` and `to1`, `to2` stay violated, as in every tool.
The stop rule (a change that would create a missed violation) did not trigger: the change
only turns blocked into enabled, so it can only remove weakly fair cycles, and it removes
them exactly where the definition does.

### 11.4 The claim need not be the last process (review finding 1)

Copy k of the n + 2 copies stands for system process k - 1; `blocked(k-1)`, the `moved` test
of `apply` and the name in the null-step note read that as process index k - 1, which holds
only when the claim is last. The Promela frontend, the LTL claim and `np_` append it
last; an IR from `--ir` or an inline `ir` argument of `mc_check` need not. With the claim
first or in the middle copy 1 was the claim, so every cycle was lost and the engine said
`verified` on a model with a weakly fair accepting cycle, in both binaries (0.2.0 too).
`cycleSearch.sys` lists the non-claim processes and the three places use `sys[k-1]`
(`431bd00`). Red: `TestWeakFairnessClaimNeedNotBeLast` (all six orders of the processes of
the review's `ir1`, none and weak; the four orders with the claim not last failed under weak
fairness with `verified`) and a scenario outline over `testdata/ir/weakfair-claim-{last,first,
middle}.json`. The oracle generator now puts the claim at a random position too.

### 11.5 Three defects the extended oracle and the new generator found

1. **Timeout moves of every claim edge** (`c1de020`; a missed violation, 0.2.0 too, with and
   without fairness). The product search enumerates the system's moves once per enabled claim
   edge; the timeout phase of `nextEnabled` starts when the frame's `enabled` counter is
   still zero after the ordinary moves, and the first claim edge's timeout moves raised it,
   so no later claim edge ever got the timeout moves. A claim with two enabled edges in a
   timeout state (any nondeterministic claim, as an LTL automaton has) lost the transitions
   of all but the first: `weakfair-timeout-claim.pml` (`P: do :: timeout od`; claim: stay on
   c0 or go to a looping accept location): pan -a 2 errors, -a -f 1; the engine `verified`.
   A weak-fairness null step raised the counter as well (without a claim, the copy of a blocked
   process offered a null step and then no timeout moves, and a stutter step instead):
   no verdict changed on the random models, but the product lost half its states
   (`weakfair-timeout-null.pml`: 8 instead of the 16 that `testdata/weakdecision/copies_tc3.py`
   derives from the construction alone). `frame.sysMoves` counts the moves of the current
   claim edge and is handed to `nextEnabled`. On the corpus the effect is visible as a state
   count: `CH2/protocol` (it uses `timeout`) with `--progress` stored 36 product states, pan
   `-l -c0` stores 63, the engine now 63; the verdict (`verified`) did not change. Red: three
   scenarios and two rows of the pan outline.
2. **`else` in a never claim** (`44d8bae`; false violations, 0.2.0 too). The edges of a claim
   are enumerated by their guards and an `else` has none, so it was always enabled; a claim
   that had to keep looping could fall off its closing brace and the engine reported "end
   state in claim reached". `claim-else-idle.pml`: pan finds no error, the engine said
   `violated`. Found on two generated models that `spin` refuses but the oracle decides
   (`m20274`, `m20587`); the oracle always implemented `else` correctly and had agreed on the
   earlier sets because those claims rarely made it matter. The random generator now adds
   `else` edges to claims, some into an `end` location (without the fix 42 rows of the
   default 3,000 models disagreed). On the pre-existing generated weak-fairness models
   `m7249`, `m8290` and `m8676` the sweep state counts drop to 2, 4 and 4 (before 4, 6, 8;
   `pan -a -c0` stores 2, 3 and 4): the statuses did not change.
3. **A consequence, to read together with §10.7.** For 19 of 3,000 generated models (all of
   them with `else` in the claim, `violated` in pan with 3 to 1,271 errors) the old engine's
   `violated` was the spurious "end state in claim reached" and carried no lasso; the real
   acceptance cycle that the engine now finds goes through the lasso rendering, which has the
   unmerged panic. The verdict is reached; the report is not produced. Another reason for
   merging `fix/cycle-lasso-panic` first.
