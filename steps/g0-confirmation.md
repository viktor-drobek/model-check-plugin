# G0 — подтверждение (протокол, п. 6)

Шаг: **G0** (план 14 §9, строка после K1). Критерий выхода: «`petrinet1` → тупик `t1, t4`; `petrinet2` даёт воспроизводимый результат; тесты бюджетов; накладные расходы интерпретации IR относительно Spike измерены и не превышают 20×».

**Соответствие критерию выхода: выполнен.** Все четыре части критерия подтверждены сценариями feature-файла и замерами ниже; оговорки — в §3.3 и §6 (что именно измерено и что отложено).

## 1. Что сделано

- `features/g0-engine.feature` — написан до кода (коммит `G0: feature file … (before code)`); 16 сценариев, из них один outline с двумя примерами: petrinet1 тупик `t1, t4` с маркировкой `p2=1 p5=1` и обратным отображением на имена пользователя; petrinet1 `safe` verified при полном обходе в 6 состояний; petrinet2 golden (два прогона байт-в-байт, равенство golden-файлу); отказ inhibitor-дуги с объяснением по Holzmann §8.10 и указанием перехода; отказ по схеме с путём `transitions[0].inputs[0].weight`; переполнение ёмкости → `invalid-model` для обоих свойств с трассой `produce, produce`; исчерпание бюджетов states / depth / time → `inconclusive` с названием ресурса и `complete=false`; та же модель в бюджете → verified/complete; DFS против BFS (свидетель `t1, t2, t3` против `t4`); IR round-trip через `mcd parse` (байт-в-байт) и совпадение отчётов `--ir`/`--petri` с точностью до секции `inputs`; origin у каждой переменной и ребра; `mcd version`; отсутствующий файл → код 1; версия движка и sha256 входов в отчёте.
- `engine/ir/` — IR по плану §5.1: переменные `bit/bool/byte/short/int` с необязательным сужением домена (`min`/`max`) и массивы фиксированной длины; процессы как графы управления с рёбрами `guard → effect`, флагом `atomic` (семантика «процесс сохраняет исключительное управление после ребра», как внутри Promela `atomic {}`; блокировка снимает исключительность), необязательным `assert`; каналы объявлены и занимают место в векторе (операций нет — G1); метки `end`/`progress`/`accept`; `origin` {file, line, name} у каждого элемента; свойства `deadlock`/`invariant`/`reach`/`assert` внутри модели. Типизированный AST выражений (арифметика, сравнения, булевы связки, чтение переменных и массивов) с детерминированным вычислителем; деление на нуль и выход за границы массива — ошибки вычисления → `invalid-model`. Раскладка состояния: байт исключительного управления, на процесс — pc и локальные, глобальные, буферы каналов; `Validate` с путями к ошибке; JSON с запретом неизвестных полей.
- `engine/frontend/petri/` — `schema.json` (draft 2020-12) и валидатор, повторяющий её по пунктам (тест сверяет список свойств схемы со списком валидатора); кодировка как в `App_C/petrinet1`: место = глобальный `byte` (при ёмкости < 255 — `max`), сеть = один процесс `init` с одной локацией и самопетлёй на переход, guard `p > 0` (или `p >= w`), эффект — декременты, затем инкременты; свойства `deadlock` и `safe`; inhibitor-дуги отвергаются с объяснением; вектор состояния petrinet1 — 8 байт (6 мест + pc + excl).
- `engine/explore/` — компактное множество посещённых (64-битные хеши, арена полных векторов, обращение по индексу) по умолчанию, map — эталон в тестах; DFS с явным стеком кадров `{индекс состояния, позиция итератора (процесс, ребро), счётчик разрешённых}` — преемники не материализуются (обязательное исправление K1); BFS с родительскими ссылками; порядок «процесс, затем ребро»; тупик по определению из feature; инварианты и `reach` на каждом новом состоянии; `assert` на шаге; переполнение домена → `invalid-model` со трассой до шага; бюджеты states / depth (отдельный, состояния глубже D хранятся, но не раскрываются) / time (deadline контекста) / memory (оценка) → `inconclusive` с причиной; `complete=true` только при полном раскрытии графа; ранняя остановка, когда все свойства решены.
- `engine/cex/` — трасса: шаги {процесс, команда, изменённые переменные до/после, локация, origin}, полное конечное состояние, `summary`; для G0 конечный путь.
- `engine/report/` — JSON фиксированного порядка: engine {name, version, ir_schema, report_schema}, inputs с sha256, model, search {mode, budget, stop, complete}, properties [{id, kind, text, status, evidence, counters {states, transitions, depth, time_ms?, memory_bytes_est}, complete, counterexample?, witness?, reason?}]. `Build` отказывает в документе, нарушающем правила K1 (verified без complete для deadlock/invariant/assert; violated или verified не с exhaustive; inconclusive не с bounded/причиной; unknown).
- `engine/cli/` + `cmd/mcd/` — `mcd parse --petri|--ir`, `mcd check (--petri|--ir) [--budget-states N] [--budget-depth N] [--budget-ms N] [--budget-mem-mb N] [--bfs] [--no-timing]`, `mcd version`; коды выхода 0 (результат есть), 2 (вход отвергнут, JSON-ошибка на stdout), 1 (ошибка инструмента). Умолчания бюджетов — «средняя модель» A4: 1e6 состояний, глубина 1e6, 60 с, 1 ГиБ.
- `engine/testdata/` — `petri/{petrinet1,petrinet2,inhibitor,bad-weight,overflow,bfs-shortest}.json`, `ir/counters-10-{5,6}.json` (порождаются `MCD_GEN_TESTDATA=1 go test ./explore -run TestGenerateTestdata`, см. `ir/README.md`), `golden/petrinet2.report.json`.
- `engine/steps_g0_test.go` — step definitions через `stepRegistrars`; все шаги идут через `cli.Run` в процессе.
- `steps/g0-logika.md` — ревью: 9 находок (3 критичных), все исправлены.

## 3. Замеры

Машина: linux/arm64, 8 ядер, 13 ГБ RAM; Go 1.26.0; SPIN 6.5.2; `gcc -O2 -DNOREDUCE`. Машина в этой сессии разделялась с другим агентом; числа Spike сняты **в той же сессии** тем же бинарником (`scratchpad/spike`), потому что сравнивать с числами из `spike-confirmation.md` (0,85 M states/s на 1e5) некорректно — сегодня тот же бинарник дал 0,18–0,28 M. Два прогона на конфигурацию; RSS — `/usr/bin/time %M`.

### 3.1. Дифференциальная проверка против pan (`spin -a`; `gcc -O2 -DNOREDUCE`; `./pan -c0` и `./pan`)

| Модель | pan: класс ошибки | pan stored `-c0` | mcd states (полный обход) | Сверка | Первый свидетель pan (`spin -t`) | Свидетель mcd |
|---|---|---|---|---|---|---|
| `App_C/petrinet1` | invalid end state, depth 3 | **8** | **6** | 8 − 2 = 6: два состояния после `p1 = 1`, `p4 = 1` в `init` Promela; у IR начальная маркировка — начальные значения, а не шаги | строка 15 (t1), строка 18 (t4) | `t1, t4`, маркировка `p2=1 p5=1` |
| `App_C/petrinet2` | invalid end state, depth 3 | **22** | **20** | 22 − 2 = 20, та же поправка | строка 14 (T1: P1 → rc, P2), строка 22 (t1: p1 → RC, p2) | `T1, t1`, маркировка `P2=1 RC=1 p2=1 rc=1` |
| `CH2/mutex_flaw.pml` (IR вручную, юнит-тест) | assertion violated | 429 (из Spike) | 429 | точное совпадение | — | `cnt=2` на `assert(cnt == 1)` |
| `counters` K=10 N=5 / N=6 | нет ошибок | 100 000 / 1 000 000 (из Spike) | 100 000 / 1 000 000 | = K^N | — | — |

Класс вердикта, число состояний (с одной и той же поправкой +2) и — как наблюдение, не гарантия — первый свидетель совпали на обеих сетях. Результат petrinet2 после этого согласования записан в `testdata/golden/petrinet2.report.json` (regression pin; см. ревью, находка 7). Совпадение первого свидетеля объясняется тем, что pan перебирает альтернативы `do` в порядке текста, а IR — рёбра в порядке объявления переходов; это не проверялось на других моделях.

### 3.2. Интерпретация IR против Spike (условие K1: < 20×)

| Модель | Движок | states/s | wall | peak RSS | байт/состояние |
|---|---|---|---|---|---|
| counters 1e5 | spike compact (сессия G0) | 0,18–0,28 M | 0,37–0,65 с | 83–91 МБ | 37 (из K1) |
| | **mcd, IR интерпретируется, DFS** | **0,57–1,32 M** | 0,08–0,19 с | **20–23 МБ** | 82 (оценка `memory_bytes_est`: арена + таблица + стек 1e5 кадров) |
| | mcd, BFS | ≈ 2,2 M (45 мс) | 0,04 с | 15 МБ | 60 |
| counters 1e6 | spike compact (сессия G0) | 0,17–0,24 M | 4,7–6,6 с | **809–850 МБ** | 32 (из K1) |
| | **mcd, IR интерпретируется, DFS** | **0,65–0,90 M** | 1,1–1,6 с | **169–174 МБ** | 75 |

Что видно:
- **Множитель интерпретации < 1**: интерпретируемый IR быстрее захардкоженного Spike в 3–4 раза на тех же моделях в той же сессии. Причина не в интерпретаторе, а в устранённом дефекте Spike: материализация всех N преемников каждого кадра давала 1,2 M аллокаций на 1e5 состояний; в G0 кадр держит индекс состояния и позицию итератора, преемник вычисляется в один переиспользуемый буфер. Сама интерпретация (обход AST guard `true`, одно присваивание `c = (c + 1) % K` с двумя операциями) на этой модели дёшева; **условие K1 «< 20×» выполнено с большим запасом**, но на модели с пустыми guard'ами — множитель на guard'ах из нескольких конъюнктов (petrinet2: до 2 конъюнктов, mutex_flaw: 2) отдельно не измерялся, обе модели слишком малы для измерения времени.
- **Peak RSS на 1e6 упал с 0,8 ГБ до 0,17 ГБ** — обязательное исправление K1 подтверждено числом. Оценка `memory_bytes_est` (75 МБ) ниже RSS из-за удвоений арены/таблицы и кучи Go.
- `байт/состояние` у mcd выше, чем у Spike (75–82 против 32–37), потому что (а) вектор длиннее (8 байт: excl + N pc-байт + N локальных против 5–6), (б) в оценку входит DFS-стек глубиной 1e6 × 32 байта = 32 МБ на этой цепочечной модели; на моделях с ветвлением стек мал. При векторе 128 байт и 1e6 состояний ожидание ~ (128 + 12) × 2 + стек ≈ 300 МБ — граница A4 (1 ГБ) держится.
- Ориентир A4 «1e6 состояний за 60 с» на этой модели — 1,1–1,6 с.

### 3.3. Что не измерено (честно)

- Множитель интерпретации на «реальных» guard'ах и эффектах (несколько конъюнктов, массивы, short/int): petrinet1/2 и mutex_flaw укладываются в миллисекунды, время процесса доминирует. Измерение возможно в G1 на `CH3`/`CH5` моделях с ≥1e5 состояний.
- Сравнение с pan по скорости в этой сессии не повторялось (pan-числа K1: 0,9–1,4 M states/s на counters); по числам K1 mcd DFS находится в диапазоне 0,5–1,0× pan.
- Каналы: объявлены, место в векторе зарезервировано, операций нет — их стоимость неизвестна.

## 4. Решения, зафиксированные в коде и требующие внимания владельца

1. **`atomic` на ребре** = «процесс сохраняет исключительное управление после ребра» (последний оператор `atomic {}` и одношаговые команды — `atomic: false`); держатель — байт в векторе состояния; блокировка внутри последовательности снимает исключительность. Переход сети Петри — одно неделимое ребро с `atomic: false`. Совпадение с тем, как pan хранит и считает состояния внутри `atomic` (промежуточные состояния, `-o3`), — предмет G1.
2. **Exit code 2** для отвергнутого входа (в постановке шага говорилось «ненулевой — только при ошибках инструмента»): деление кодов — по признаку «есть ли результат»: 0 результат есть (любой вердикт, включая `invalid-model`), 2 результата нет — вход отвергнут (JSON-ошибка на stdout), 1 результата нет — ошибка инструмента. Если владелец хочет строго «0 при любом отказе фронтенда», изменение — одна константа в `cli`.
3. **Ранее решённый вердикт не отменяется** ни бюджетом, ни `invalid-model` в другом месте графа (посылка проговорена: свидетель-прогон сам не содержит некорректного шага). Альтернатива — «invalid-model для всех свойств без исключения» — одно условие в `explore.fail`.
4. **`reach`**: `verified` по свидетелю с `complete` возможно false; `violated` только при полном обходе. Единственное исключение из правила «verified ⇒ complete», описано в feature, `explore`, `report`.
5. **Неявное свойство `assert`**: если в IR есть рёбра с `assert`, но нет свойства kind `assert`, движок добавляет его сам (`id: assert`), чтобы проверка не была молчаливой.
6. **`--no-timing`**: `time_ms` — единственное поле отчёта, не являющееся функцией входа; golden-сценарий использует этот флаг.
7. Умолчания бюджетов CLI = границы «средней модели» A4.

## 5. Отложено и почему

- Операции над каналами, `timeout`, `progress`/`accept` — по плану G1/G4; в IR объявлены, чтобы раскладка состояния не менялась.
- Автоматический запуск `spin`/`pan` из `go test` — по плану CI; числа pan вписаны в feature и сюда как константы с версией и флагами.
- Замер интерпретации на моделях с содержательными guard'ами — G1 (нет Promela-фронтенда, а ручная IR-кодировка крупной модели — не работа G0).
- `mc_estimate`-подобная оценка роста — G5 по плану.
- Циклические контрпримеры (prefix + loop) — G4.
