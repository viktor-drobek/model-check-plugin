## 4. Решения, зафиксированные в коде (семантика; каждое — по пробе против pan)

1. Локация = точка между операторами; каждый оператор — одно ребро; `if`/`do` без собственного ребра; `goto`/`break` после оператора складываются в цель оператора (алиасинг узлов); одиночная альтернатива `:: goto L` / `:: break` — собственное ребро (pan: `goto L`, `goto :b0`).
2. Объявления — не шаги; инициализатор локальной переменной применяется при создании процесса (`byte me = _pid + 1` → `Init`), только константы и `_pid` (иначе — вне подмножества).
3. `printf` — шаг без эффекта; предупреждение о непроизведённом выводе.
4. Завершение процесса — переход `-end-` из локации с меткой `end` в мёртвую локацию; разрешён, когда ни один более молодой процесс не жив (pan удаляет только последний процесс вектора); обнуляет локальные переменные. Недостижимые локации отсекаются, как в автомате pan (у зацикленного proctype нет `-end-`).
5. pid: `active`/`init` в текстовом порядке, затем процессы `run` в текстовом порядке операторов `run` в `init`; имя экземпляра `<proctype>:<pid>`; `_pid` — константа экземпляра. Ограничение: повторное использование pid после смерти процесса, созданного `run`, не воспроизводится (движок даёт статический индекс); в CH2/CH3 не наблюдаемо.
6. mtype: внутри декларации последний = 1 и далее вверх; следующая декларация продолжает выше (проба: `{a,b} {c,d}` → 2 1 4 3).
7. `atomic`: ребро с целью внутри блока держит исключительное управление; последнее — нет; промежуточные состояния не хранятся (см. §3.1). `d_step`: одно ребро-вход с продолжением внутри шага, недетерминизм внутри — первая разрешённая альтернатива (проба dn: 3 состояния), блокировка — `invalid-model`; rendezvous внутри `d_step` — вне подмножества.
8. Rendezvous — один шаг отправитель+получатель, каждый подходящий получатель — отдельный переход; в трассе — `partner`.
9. `else` — динамически: разрешён, когда не разрешено ни одно другое ребро той же локации. `timeout` — двухфазно (истина ⇔ при timeout = false не разрешено ничего).
10. Переполнение домена (byte/short/int, ёмкость канала) — `invalid-model` по плану 14 §4.1; pan усекает молча — три файла CH3 расходятся по замыслу.
11. Never claim — процесс с `Claim: true`, не исполняется, предупреждение; пары `#ifdef PHI` выбираются `-D`.
12. Инварианты/`reach` проверяются на хранимых состояниях (промежуточные состояния `atomic` скрыты от них, как от claim у SPIN); `assert` — на каждом шаге.
13. Отказы фронтенда: `kind ∈ {syntax, semantic, outside-subset}`, всегда `status: not-executed`, путь `file:line:col`, сообщение с конструкцией, файлом и строкой; `invalid-model` — только из выполнения.

## 5. Отложено, отклонения от плана, K2

- **Сужение подмножества (требует решения владельца):** план 14 §5.2 включает `run` с аргументами без ограничений; движок принимает `run` только как линейный оператор `init` (не в `proctype`, не в альтернативе/цикле), потому что процессы инстанцируются статически, а pid и число процессов при `run` из нескольких процессов зависят от переплетения. Следствие: `CH3/splurge{,2}.pml` (рекурсивное `run`, у pan — «aborting» по лимиту процессов) и вне глав 2–3 `CH14/v14_10`, `v14_14`, `CH15/eratosthenes*` отвергаются как «вне подмножества, принимаемого движком». Рекомендация: либо записать сужение в план §5.2 (MVP), либо поднять динамическое создание процессов в v1 (G5) вместе с `_nr_pr`.
- **Переполнение byte** — три файла CH3 расходятся с pan по решению плана §4.1; если владелец захочет режим «усекать, как SPIN», это один флаг при записи в слот (`store1`).
- **K2 (контрольная точка после G1).** Знаменатель по плану §4.1 — файлы глав 2–3 «без `inline`, `typedef`, `unless`, `provided`»: 36 − 6 = 30. В подмножестве движка: 24 (80 %), из них точное согласие с pan — 21 (70 %), 3 — расхождение по политике переполнения. Остальные 6: `rendezvous2` (канал в сообщении — план v1), `splurge`/`splurge2` (сужение выше), `wc` (канал `STDIN` без инициализации — pan тоже даёт ошибку), `notpossible`, `scope` (отвергает и SPIN). Доля ниже порога 90 % → по плану §9 расширение подмножества замораживается до разбора расхождений; разбор дан здесь: все шесть объяснены, ни одно не является дефектом кодировки. Трудозатраты G1 относительно оценки 14–20 pd — по факту одна сессия; пересчёт G4–G6 — владельцу.
- Имена mtype в трассах (сейчас числовые значения; текст команды показывает исходный оператор) — удобство, отложено.
- Блочные повторные объявления локальных переменных (SPIN 6 допускает) — вне подмножества с сообщением; в корпусе не встречаются.
- `else` рядом с rendezvous, `timeout` внутри `atomic`, получатель rendezvous внутри `atomic` — реализованы по общим правилам, пробы против pan не делались (нет в CH2/CH3).
- Бесконечный цикл внутри `atomic` (нехранимые состояния) упирается в бюджет глубины → `inconclusive` с причиной, как pan в лимит глубины; отдельного сообщения нет.
- Исполнение never claim (синхронное произведение), `progress`/`accept` — G4; поле `AtomicSteps` в отчёт не выведено (не менять схему отчёта в G1).
