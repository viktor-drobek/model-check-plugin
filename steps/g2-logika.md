# G2 — логическое ревью (протокол, п. 5)

Предмет ревью: `features/g2-mcp.feature` (шапка и сценарии), документирующие комментарии пакета `engine/mcp` (`server.go`, `session.go`, `guard.go`, `budget.go`, `parse.go`, `check.go`, `simulate.go`, `lint.go`, `estimate.go`), `explore/step.go`, тексты статусов, причин (`reason`), заметок (`budget_notes`, `warnings`) и сообщений об ошибках инструментов. Метод — skill `logika` (режим ревью): выделены тезис и посылки, проверены понятия (закон тождества, деления) и правила вывода, ошибки названы по каталогу `references/errors.md`. Отдельно проверены три вопроса постановки шага. Найденное исправлено в тех же файлах до написания подтверждения (коммит «G2: logika review fixes»); одна находка (№ 11) получена не чтением, а прогоном бинарника по stdio — она включена, потому что это противоречие между feature и реализацией.

**Вердикт:** найдено 14 ошибок (4 критичных, 10 спорных); 13 исправлены, 1 (№ 13) — осознанная омонимия, закреплённая документацией.

**Структура аргументации.** Тезис артефактов шага: «через семь инструментов MCP skill получает те же результаты, что через CLI, при этом (а) три рода ответов — отказ инструмента, отвержение входа, результат проверки — различимы (NFR-007); (б) каждое свойство несёт ровно один статус словаря 11 §14; (в) лимиты применяются внутри сервера и не могут быть превышены клиентом; (г) ни один файл не может быть записан вне каталога сессии». Посылки: (1) ошибка Go из типизированного обработчика превращается SDK в результат с `isError = true` без структурного содержимого, а структурные ответы `isError` не несут; (2) статусы назначаются только движком G0 (`explore`/`report`), сервер их не создаёт, а только переписывает `reason` для ltl/ctl/progress; (3) все файлы инструментов проходят через один писатель `Session.WriteFile` → `Resolve`; (4) `Clamp` даёт умолчание при 0 и потолок при превышении, а умолчания заранее вписаны в потолки (`within`); (5) схемы выводятся из Go-структур, поэтому документация полей и валидация совпадают. Вывод: сценарии feature наблюдают через клиент MCP ровно то, что реализовано.

**Проверка трёх вопросов постановки.**

- *Является ли множество из шести статусов исчерпывающим делением в каждом обработчике?* Статусы свойств пишет только `mc_check`, и берёт их из `report.Build` над `explore.Result` — деление, проверенное в G0 (`TestStatusPartition`, отказы `Build`). Сервер добавляет к статусам ровно две операции: переписывание `reason` для kinds ltl/ctl/progress (статус не меняется) и `aggregate` — выбор одного из уже назначенных статусов по фиксированному порядку; после исправления № 4 агрегат никогда не порождает статус, которого нет у свойств. Остальные обработчики статусов свойств не выдают: у `mc_parse` — собственное трёхчленное деление `outcome ∈ {ir, rejected, not-executed}` (каждая ветвь возврата без ошибки устанавливает ровно одно значение); у `mc_simulate` — семичленное `stopped` (каждый выход из цикла устанавливает одно значение; внутренняя проверка `Stopped == ""` замыкает деление ошибкой инструмента, а не выдумкой); у `mc_estimate` статусов нет вовсе, и ответ говорит об этом (`note`). Итог: деление исчерпывающее, члены не пересекаются; единственная дыра (агрегат над пустым списком) закрыта.
- *Отделены ли «ошибка сервера» и «результат проверки» (NFR-007)?* Механизм: ошибка Go из обработчика → SDK строит `CallToolResult{IsError: true, Content: text}` без `StructuredContent` (проверено чтением `server.go` SDK v1.8.0, строки 421–433: обычная ошибка оборачивается в результат, `jsonrpc.Error` уходит протокольной ошибкой — таких сервер не возвращает). Результат проверки — всегда структурный ответ с `isError = false`, даже при `violated`/`invalid-model`/`not-executed`. Юнит-тест `TestToolErrorIsNotAResult` и шаг feature «the call is an error whose message mentions …» проверяют, что у ошибки нет структурного содержимого. Класс «отвержение входа» — третий: `outcome: rejected` у двух инструментов с документом результата и префикс `rejected input (<kind>):` у трёх без него (№ 3). Четыре класса NFR-007: syntax/schema → rejection; model → `invalid-model` (статус движка); tool → `isError`; resource → `inconclusive` с ресурсом в `reason`.
- *Всегда ли причина `not-executed` называет отсутствующую возможность?* Источники `not-executed`: (а) `mc_check` для ltl/progress/ctl — таблица `notExecutedReason` называет возможность (LTL→Büchi и nested DFS; поиск циклов без прогресса; CTL-разметка) и шаг (G4/G5); (б) `explore.initOutcomes` для иных kinds, пришедших из IR модели, — текст движка называет kind, который не исполняется, и перечень исполняемых; (в) `mc_parse` для Promela — называет фронтенд (`engine/frontend/promela`), шаг (G1) и выход (передать petri/ir). Для `mc_lint_property` временные формулы не получают статуса вовсе — это ошибка инструмента с названием шагов G4/G5, что правильно: lint не является проверкой. Предупреждение о `fairness weak` тоже называет G4. Случая `not-executed` без названной возможности не найдено.

**Скрытые посылки.**
- «SDK превращает обычную ошибку в `isError`-результат» — верно для закреплённой v1.8.0 (прочитан код); при смене версии SDK посылку надо перепроверить (юнит-тест `TestToolErrorIsNotAResult` сломается первым).
- «В каталог сессии между проверкой и записью никто не пишет» (TOCTOU) — проговорена в `Resolve` (№ 10); при разделяемом базовом каталоге «невозможно» ослабляется до «невозможно для клиента инструментов».
- «Имена рёбер (текст, origin.name) уникальны» — не требуется: при нескольких разрешённых ходах с одним именем guided-режим берёт первый в порядке explorer'а; проговорено в `nameMatches`; `process/index` уникален всегда.
- «`json.Marshal` карты даёт канонический JSON» — верно для `encoding/json` (сортировка ключей); на этом держится воспроизводимость sha256 inline-входов (№ 7).
- «Деление статусов G0 сохраняется после правок explorer'а в G1 (rendezvous, timeout, d_step)» — не перепроверялось в G2; сервер опирается на `report.Build`, который отказывает в документе с нарушением правил, так что нарушение проявилось бы ошибкой инструмента, а не ложным статусом.
- «Открытая схема `{}` для поля `ir` достаточна» — вход не валидируется схемой SDK, а проверяется `ir.UnmarshalJSON` (запрет неизвестных полей, `Validate`); отвержение — структурное (`rejected`), а не ошибка валидатора.

**Сила недедуктивных выводов.**
- 31 строка сценариев на petrinet1/petrinet2/counters и 9 юнит-тестов — индукция, достаточная для вывода «каждый инструмент отвечает, каждый лимит срабатывает на этих моделях», недостаточная для вывода о произвольных IR (это риск движка, а не сервера: сервер не считает состояний).
- «Запись вне каталога сессии невозможна» — вывод дедуктивный из строения кода (один писатель → один guard) при посылке TOCTOU; 13 форм путей в `TestResolve` (включая symlink наружу, symlink внутрь, лексический выход, абсолютный путь внутри каталога) и 3 сценария feature подтверждают, что guard делает то, что сказано, а не то, что guard стоит на всех путях — второе доказывается чтением: `os.WriteFile` встречается в `engine/mcp` один раз, в `Session.WriteFile`.
- Прогон по stdio — единичное наблюдение, что транспорт stdio ведёт себя как in-memory; достаточен для обнаружения расхождения (№ 11), недостаточен как доказательство эквивалентности транспортов — она следует из того, что оба используют один `mcp.Server`.
- Аналогия «умолчания CLI = умолчания MCP» — намеренная и слабая в одном месте: 0 в CLI означает «без лимита», в MCP — «умолчание»; различие проговорено в doc `Budget`, чтобы skill не перенёс привычку с одного интерфейса на другой.
