# G3 (документационная половина) — подтверждение

Шаг плана 14 §9: **G3** — `SKILL.md`, references, assets, evals E1, E3, E5.
Критерий выхода в плане: «E1/E3/E5 проходят assertions; baseline без skill — нет».

## Соответствие критерию выхода

**Выполнен частично: документационная половина сделана полностью; половина с
прогоном evals (E1/E3/E5, baseline без skill) отложена**, потому что она требует
работающего движка и MCP-сервера (шаги G0–G2), которых на момент этого шага нет.
Файл `evals/evals.json` содержит шесть промптов плана §8.2 (E1–E6) с пустыми
списками ожиданий; assertions будут добавлены при прогоне. Проверяемая часть
критерия для этой половины зафиксирована в `features/g3-skill-package.feature`
(20 сценариев) и вся зелёная.

## Замеры

Не применимо (документационный шаг). Размеры: SKILL.md 216 строк тела; references
1392 строки суммарно; самый длинный — pitfalls.md (218).

## Отложено и почему

- Прогон evals E1/E3/E5 с skill и без, assertions, просмотр человеком — нужен
  движок + MCP (G0–G2). Промпты и fixtures готовы.
- Точная схема ответов инструментов (имена полей `status`, `evidence`, входов
  `fairness`, `mode`) — фиксируется в G2; в `engine-tools.md` названия даны по плану
  §6 и помечены как иллюстративные до G2.
- Порядок приоритетов при назначении статуса движком (evidence-and-status.md §2) —
  описан как ожидание, подлежит сверке со схемой результата в G2.
- Способ представления атома `fire(t)` во frontend сетей Петри — решение G0.

## Добавленные зависимости

Нет. `engine/skillcheck` — пакет без внешних зависимостей, используется только из
тестов.

## Рекомендации, требующие правки плана 14 (сам план не менял)

1. **§5.2 (подмножество Promela).** Явно назвать конструкции, которые нужны уже
   MVP-моделям корпуса, но в списке отсутствуют: `_pid` (`CH2/mutex_flaw.pml`),
   форма `mtype { … }` без `=` (`CH4/dijkstra_progress.pml`), `nempty`/`nfull`,
   препроцессорные условия `#ifdef`/`#if 0`/`#else`/`#endif` (`CH4/prop.pml`).
   Решить судьбу `xr`/`xs` (в корпусе только под `#if 0`) и `_nr_pr`
   (`CH15/client_server.pml`, отнесён к v1).
2. **§4.1 / §5.2 (семантика).** Зафиксировать реакцию движка на блокировку внутри
   `d_step` (в skill описано как ожидание `invalid-model`) и подтвердить отсутствие
   режима потери сообщений при переполнении канала.
3. **§6 (результат `mc_check`).** Зафиксировать в схеме результата порядок
   приоритетов статусов (not-executed → invalid-model → violated → verified →
   inconclusive → unknown) и правило «evidence `bounded` — когда движок может
   назвать границу покрытия, `unknown` — когда не может», как это описано в
   `evidence-and-status.md` §2–§3; либо поправить skill под фактическую схему.
4. **§8.2 (evals).** В `evals.json` поле называется `expectations` (схема
   skill-creator), а план говорит «assertions»; стоит закрепить одно имя.
