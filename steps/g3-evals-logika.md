# G3 (половина evals, стадия 2 после G1) — логическое ревью (skill `logika`, режим «Ревью»)

Объект ревью: (1) переписанные справки `skills/model-check/references/promela-subset.md`
и `references/engine-tools.md`, правка шага 3 `SKILL.md`, дополнения
`evals/fixtures/README.md`; (2) `features/g3-evals.feature`; (3) правка одной assertion в
`evals/evals.json` (E5 № 5); (4) рассуждения трёх with-skill прогонов —
`evals-workspace/iteration-2/eval-{1,3,5}-*/with_skill/outputs/answer.md` — с вопросом
«заставил ли skill агента утверждать больше, чем позволяют свидетельства, и где именно»;
(5) заметки `benchmark.md`. Проверялись: соответствие утверждений тому, что движок
реально делает (пробы `mcd` на `CH2/mutex_flaw.pml`, `CH17/simple1.pr`, `CH4/prop.pml
-D PHI`, `mcd serve` по stdio), полнота делений, безусловные утверждения без основания,
подмена понятий, противоречия между файлами. Транскрипты — свидетельства прогона; они не
правились, находки по ним переведены в правки справок и рекомендации.

**Вердикт:** найдено 14 ошибок (4 критичных, 10 спорных). Критичные и 4 спорные
исправлены в файлах (колонка «Исправление»); 6 спорных проговорены и отнесены к
рекомендациям (правка чужих файлов или транскриптов не допускается).

**Структура аргументации.** Тезис шага: «после G1 evals E1 и E5 проходят assertions со
skill и не проходят без него; справки описывают движок, который построен в G1/G2».
Посылки: (а) движок — единственный источник фактов о подмножестве, CLI, MCP и отчёте;
(б) assertions — объективные проверки формы (регулярные выражения по тексту ответа и
структурные проверки артефактов), содержание проверяет человек по `review.html`;
(в) прогон субагентом с путём к `SKILL.md` = «со skill», прогон с одним промптом =
«без skill». Автор выводит описание подмножества и инструментов дедуктивно из
`steps/g1-confirmation.md`, `steps/g2-confirmation.md`, кода и проб; вердикт по критерию —
индуктивно из шести одиночных прогонов (три пары).

**Скрытые посылки.**
- «Прогон субагента с путём к `SKILL.md` и бинарником — это то, что сделает Claude Code
  с установленным плагином». Посылка неполная: путь MCP (`mc_*` через `mcd serve`) не
  упражнялся вовсе, и в текущей сборке он для Promela и не работает (`mc_parse` →
  `not-executed`, фронтенд не подключён в `serve.go`). Вердикт по критерию относится к
  CLI-пути `SKILL.md` шаг 3; G6 должен повторить прогон через реальный плагин.
- «Regex-assertions измеряют выполнение контракта skill'а». Верно для различающих
  assertions (движок вызван, словарь, evidence, manifest, `not-executed`), но, как показали
  № 3 и № 9, регулярное выражение одинаково пропускает и правильное поведение (перепись)
  и неверное (хост-код выполнен) — оценка формы, не содержания. Просмотр `review.html`
  человеком остаётся частью критерия плана §8.2, а не украшением.
- «Baseline без skill — честный baseline». Он работал в том же репозитории: E5-baseline
  нашёл `mcd` сам (и увидел `outside-subset`), E1-baseline воспользовался установленным
  SPIN. Это делает baseline **сильнее**, чем «чистый» агент без инструментов, и,
  следовательно, наблюдаемый разрыв — оценка снизу, не сверху.

**Сила недедуктивных выводов.** Вывод «критерий стадии G1 выполнен» — индукция из трёх
пар одиночных прогонов одной модели в один день: with-skill 8/8, 10/10, 7/7 против 4/8,
5/10, 5/7. Разрывы велики относительно шага одной assertion (наименьший — 2 из 7), и все
различающие assertions лежат в одной категории (контракт skill'а), что делает
объяснение «случайность» маловероятным, но не исключённым: n = 1 на конфигурацию, без
дисперсии, `benchmark.json` честно показывает `stddev` по трём разным evals, а не по
повторам. Аналогия «субагент ≈ сессия с плагином» — поверхностная в части MCP (см.
скрытые посылки). Достаточно для «выполнен» на заявленной стадии; недостаточно для
любых количественных утверждений о выигрыше skill'а.
