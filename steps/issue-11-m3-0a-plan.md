# Issue #11 — M3.0a backend-contract kernel

**Parent:** issue #11, M3.0, issue #23
**Status:** proposed implementation increment, not a capability or milestone-closure claim
**Affected layer:** G0. `engine/backend` depends only on `modelcheck/ir` and the standard library. It has no CLI, MCP, report, adapter, or process-execution path.

## Purpose and boundary

M3.0a introduces the smallest versioned, fail-closed Go contract required before a specialised verification backend can be integrated. It creates neither an integration nor a public capability. The default finite explicit-state route and every existing wire schema remain unchanged.

The package is deliberately in-process and typed. JSON framing and decoding, external processes, cancellation transport, isolation enforcement, trace replay, certificate checking, independent oracle binding, model or property translation equivalence, and report translation belong to later M3.0 increments. Test fixtures are in-process Go values, not a protocol or subprocess adapter.

The existing `backend.external-unintegrated` boundary-only capability-matrix row remains unchanged. No release manifest, binary, MCP declaration, public capability documentation, or provenance record changes. The deployment-impact record must prove that assessment and prove `mcd` does not link `modelcheck/backend`.

## Normative v1 contract

`ContractVersion` is `mcd-backend-contract/1`. Public request, payload, and vocabulary values are closed Go types. `Validated` has unexported fields and can be constructed only by `Validate`; callers use accessors. The public API is:

```go
func NewRequest(spec RequestSpec) (Request, error)
func NewHostFacts(request Request, spec HostFactsSpec) (HostFacts, error)
func Validate(request Request, host HostFacts, payload Result) Validated
```

`Validate` never returns an error or rewrites a backend terminal status. It returns either the validated payload or a deterministic synthesized `contract-invalid` result with an empty property verdict and no backend-supplied provenance, numerical evidence, trace assurance, diagnostic text, or artifact claim. A zero `Validated` reads through its accessors as that same `contract-invalid` result with reason code `zero-validated`. The fixed validation order is request validity, host-fact validity and request binding, host-terminal precedence, unavailable capability, identity, backend identity, capabilities, provenance, table row, then status-specific data. It reports only one closed local reason code. Any change to this order, a table row, an enum, a reason code, a ceiling, or the identity encoding requires a new `ContractVersion`.

### Immutable request binding

`NewRequest` validates the submitted model with `ir.Validate`, serializes it with `ir.MarshalJSON`, and derives its immutable identity from the canonical model and supplied property bytes. It retains neither the mutable `*ir.Model` nor caller-owned slices or bytes, so none remain reachable from a request.

`RequestSpec` contains the contract version, nonempty expected backend ID and version, one submitted model, one nonempty opaque canonical-property byte sequence, a caller-generated nonzero `[16]byte` nonce, the required singleton capability set `{exact-verdicts}`, and four positive unsigned bounds (`states`, `depth`, `milliseconds`, `memory_mb`) no greater than `2_147_483_647`. Backend IDs, versions, and provenance strings are valid UTF-8 and at most 256 bytes. Property bytes are at most one mebibyte. A malformed model, empty or oversized property, invalid nonce, wrong capability set, or invalid bound is rejected by `NewRequest`, not converted into a backend contract failure. These ceilings preserve conversion to every supported target's `int`, `int64`, `time.Duration`, and memory-byte accounting without overflow.

`NewRequest` rejects invalid UTF-8 in every string reachable from the submitted IR, validates the submitted IR, then requires the canonical JSON to round-trip through `ir.UnmarshalJSON`. Its generic UTF-8 traversal is capped at `16_000_000` reflected values (`4 * ir.MaxIRWeight`) and `16 MiB` of aggregate UTF-8 text bytes before serialization. A conservative 256 MiB pre-serialization allowance charges each visited value and each text byte for worst-case JSON escaping. The preceding IR validation enforces the existing expression-weight limit before indentation can allocate. The traversal also charges every `RunOp` target/initializer expression check against `ir.MaxIRWeight` before calling `ir.Validate`. These counters charge repeated shared containers and strings on every use, so an in-process caller cannot force unbounded reflective work, validation work, or canonical JSON expansion. The model digest is SHA-256 of those exact canonical bytes. That established serializer uses fixed struct field order, no model maps, two-space indentation, HTML escaping disabled, and a trailing newline. M3.0a pins its bytes in a golden test. The digest identifies the canonical serialization, including origins, text, and every carried `Properties` element. It makes no claim of semantic equivalence between different IR values or between `nil` and empty slices where JSON omits both.

Property normalisation is outside G0. A future frontend provides already-normalised canonical property bytes, which M3.0a treats as opaque. The property digest is SHA-256 of those exact bytes. The request binds both the complete submitted IR and the selected property bytes. M3.0a does not assert their semantic correspondence; the future translator or independent equivalence checker owns that obligation.

The immutable request identity is SHA-256 over a length-delimited canonical tuple. Strings and byte sequences have an unsigned big-endian 32-bit byte length followed by their bytes, capability count is an unsigned big-endian 16-bit integer followed by sorted labels, every bound is an unsigned big-endian 64-bit integer, and the nonce is its fixed 16 bytes. The tuple contains contract version, IR schema, model digest, property digest, expected backend ID and version, requested capabilities, all four bounds, and nonce. The model and property SHA-256 digests enter this tuple as their 64-byte lowercase hexadecimal strings, with the same unsigned big-endian 32-bit length prefix as every other string. A result must echo that identity and the expected backend ID and version. The caller owns nonce uniqueness, so the contract prevents cross-request reuse when the caller supplies a unique nonce.

### Closed vocabulary, capability authority, and host facts

The only v1 capability is `exact-verdicts`. `HostFactsSpec` contains a strictly ascending available-capability set, exactly one host terminal, an invalid-input or backend-failure reason only when its matching terminal is selected, and resource-stop data only when that terminal is selected. `HostFacts` stores only unexported, defensive copies plus the identity of the `Request` passed to `NewHostFacts`. `NewHostFacts` rejects a zero request, an unknown, duplicate, or unsorted capability, an unknown terminal, a reason incompatible with its terminal, and resource-stop data that does not match that request. `Validate` rejects a zero or differently bound `HostFacts` with a closed reason code. A successful payload must acknowledge exactly the requested set, and every requested capability must be available. If a requested capability is unavailable and the payload is zero-valued, `Validate` synthesizes `unsupported`, naming the canonical least unavailable requested capability and acknowledging no capabilities. Thus a backend cannot self-authorise an additional capability or declare an input unsupported at will.

`HostFacts` has one mutually exclusive host terminal: `none`, `invalid-input`, `cancelled`, `isolation-refused`, `backend-failure`, or `resource-stop`. Its `invalid-input` reason is the closed `malformed-model` enum and its `backend-failure` reason is the closed `backend-execution-failed` enum. The public `ReasonCode` type also exports closed validator reasons, including `identity-mismatch`, `invalid-metadata`, `invalid-result-row`, `invalid-resource-stop`, and `undeclared-result-row`. Its resource-stop uses the resource rule below. A non-`none` host terminal takes precedence over every payload. The payload must then be zero-valued and `Validate` synthesizes the matching non-verdict result without backend provenance. A nonzero payload while a host terminal is set is `contract-invalid`. This defines both directions of host ownership and makes a simultaneous cancellation and isolation refusal impossible. `contract-invalid` is reserved for `Validate` and is never accepted from a backend payload.

Backend payload provenance has the closed fields `backend_id`, `backend_version`, `implementation`, and `build_identity`; each is nonempty and the first two match the request. It is retained only in a valid `Validated` result.

Terminal statuses are `verified`, `violated`, `inconclusive`, `unsupported`, `invalid-input`, `cancelled`, `isolation-refused`, `backend-failure`, `resource-stop`, and validator-synthesized `contract-invalid`. Host facts synthesize the non-backend rows. A property verdict is either present or absent, never inferred from status.

Numerical evidence is optional. Its closed values are `exact`, `approximate`, `certified-sound`, and `oracle-exception-reduced`. Trace assurance is required for every backend payload. Its closed values are `replayed`, `not-applicable`, `trace-absent-approved`, and `replay-unavailable-approved`. Contract-invalid reason codes, backend-failure reason codes, invalid-input reason codes, and resource phases are each closed enums defined beside their public Go types. Every backend payload row must echo the request identity. Every synthesized row carries the locally copied request identity, except zero `Validated`, which carries none. Every accepted row explicitly specifies acknowledgements, status-specific data, provenance, and reason. All fields not named by its row must be zero-valued.

The complete accepted v1 payload table is below. Every tuple not listed is `contract-invalid`.

| Terminal status | Evidence | Trace assurance | Property verdict | Acknowledgement, provenance, and status data |
| --- | --- | --- | --- | --- |
| `verified` | `exact` | `not-applicable` | present, `verified` | Echoes request identity, acknowledges `{exact-verdicts}`, has complete matching provenance, and has no reason or status-specific data. |
| `inconclusive` | `exact` or `approximate` | `not-applicable` | absent | Echoes request identity, acknowledges `{exact-verdicts}`, has complete matching provenance, and has no reason or status-specific data. Approximate evidence never becomes a verdict. |
| `resource-stop` payload | absent | `not-applicable` | absent | Echoes request identity, acknowledges `{exact-verdicts}`, has complete matching provenance, and has only valid execution-phase resource-stop data. |
| `unsupported` synthesized | absent | absent | absent | Payload is zero-valued, provenance is absent, and data names only the canonical least unavailable requested capability. |
| `invalid-input` synthesized | absent | absent | absent | Payload and provenance are absent, and data is only the host invalid-input reason. |
| `cancelled` synthesized | absent | absent | absent | Payload, provenance, reason, and status-specific data are absent. |
| `isolation-refused` synthesized | absent | absent | absent | Payload, provenance, reason, and status-specific data are absent. |
| `backend-failure` synthesized | absent | absent | absent | Payload and provenance are absent, and data is only the host backend-failure reason. |
| `resource-stop` synthesized | absent | absent | absent | Payload and provenance are absent, and data is only valid host resource-stop data. |
| `contract-invalid` synthesized | absent | absent | absent | Payload provenance and all status-specific data are absent. The only data is the validator reason code. |

M3.0a rejects every `violated`, `certified-sound`, `oracle-exception-reduced`, `replayed`, `trace-absent-approved`, and `replay-unavailable-approved` payload. It also rejects every approximate violation, including one with a self-attested replay marker. A later trace-replay-aware contract version may admit violations and the deferred evidence classes only after it owns certificate, oracle, replay, and approval validation. M3.0a therefore implements no replay attestation, trace artifact, witness, invalid-binding tuple, certificate, numerical value, or translation-equivalence claim. It checks only the evidence classification allowed above.

`resource-stop` contains a closed limiting-resource enum (`states`, `depth`, `milliseconds`, or `memory_mb`), its matching request bound, a nonempty closed phase enum (`admission` or `execution`), and one unsigned consumed amount no greater than `maxBound`. An `admission` stop may have zero consumed amount and must not exceed its bound, but it is host-owned and therefore valid only in `HostFacts`. An executed backend payload may report only an `execution` stop, whose consumed amount is at least its bound. It cannot carry a property verdict or another resource claim. M3.0a does not map this internal terminal status to `mcd-report/1`.

## Tests and observable specification

1. Add `features/g0-backend-contract.feature` before production behavior and `steps_g0_backend_test.go` with `registerG0BackendSteps`. The steps use only public `backend` APIs and are registered in the root feature harness. First make a defined assertion fail against a minimal contract scaffold, then implement the row it specifies.
2. The feature file covers every accepted payload and host-synthesized row, request-identity mismatch, wrong backend ID or version, malformed model rejected by `NewRequest`, capability authority, host-terminal precedence, missing required provenance, invalid bounds or nonce, every invalid resource-stop field, and every denied evidence or trace class.
3. Package tests enumerate the full cross-product of backend terminal status, evidence presence and class including absence and unknown values, trace assurance including absence and unknown values, verdict presence or value, acknowledgement, requested and available capability sets, provenance, reason, and status-specific data. They assert that precisely the table rows validate and that every other tuple synthesizes the empty deterministic `contract-invalid` result. They include request identity, host-fact, reason-code, and bound permutations.
4. Package tests pin the `ir.MarshalJSON` fixture bytes and request digest. They prove deterministic identities over repeated construction and independently reconstructed model values, and prove binding changes for model, property bytes, backend version, capability set, each bound, and nonce. Tests prove that `NewRequest`, request-bound `NewHostFacts`, `Validate`, and every `Validated` accessor make defensive copies. A parallel mutation and accessor test runs under `-race`.
5. Test helpers use typed fixture values only. There is no JSON-line protocol, decoder, `go run`, checked-in binary, child process, or bounded-reader claim in this increment. A future decoder and out-of-process adapter must specify schema, duplicate and case-variant member rejection, unknown-field rejection, trailing-data rejection, and byte and depth limits before accepting untrusted protocol input.

## Exit evidence

M3.0a is complete only when the feature harness, package table and identity tests, focused and full tests, race test, static and security checks, rule sync, deployment-impact assessment, confirmation record, final blind review, and policy-required two-host confirmations pass. It neither closes M3.0 nor issue #23 and does not claim an external backend or report integration. Later increments still require protocol decoding, an isolated out-of-process adapter, cancellation and isolation enforcement, trace replay, provenance retention outside the validated value, certificate validation, independent oracle binding, model and property translation equivalence, CLI and MCP representation, contract-version propagation to reports and the matrix, and the complete M3.0 conformance-harness matrix.
