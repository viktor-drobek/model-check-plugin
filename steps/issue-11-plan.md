# Issue 11 — verification capability and conformance roadmap plan

> **Status.** Draft implementation plan for [issue #11](https://github.com/viktor-drobek/model-check-plugin/issues/11). This document plans work only. It does not claim that a capability is available until the corresponding acceptance evidence has been recorded.
>
> **Scope.** The roadmap expands the engine beyond its current finite explicit-state boundary and makes the model-to-implementation claim reviewable. It does not promise to eliminate state-space explosion or to verify arbitrary unbounded programs.

## 1. Starting point and planning rules

The tracker remains open. Its comments record completed slices that this plan must preserve rather than repeat.

- Issues #3, #6, #7, #8, and #10 are closed.
- The resource-control work covers source input and persisted report or trace artifacts. Rolling manifest retention remains a separate policy concern.
- The conformance workflow, dossier template, and deliberate mismatch example are shipped.
- The CTL-only path can build an eligible reachable graph in parallel. CTL labelling and witness reconstruction remain sequential.
- A guarded linear brace-block subset of Promela `unless` is implemented locally. The broader Promela workstream and issue #17 remain open.

Every milestone in this plan follows these rules.

1. Work at the lowest affected layer first. Core and IR changes precede frontends, then CLI and MCP surfaces, skill material, and packaging.
2. Add an observable Gherkin scenario before implementation. Keep unit, differential, and oracle tests beside the code that owns the behavior.
3. State supported semantic classes, assumptions, limits, status, and evidence in every user-visible result. A limit, backend failure, or numerical ambiguity must never become a successful verdict.
4. Preserve the default CPU explicit-state path and its wire contracts unless a versioned migration explicitly changes them.
5. Run capacity admission before model checking, fuzzing, race tests, benchmarks, or full suites. Bound every such run by time, state, depth, memory, and scratch-space policy.
6. Before declaring an issue slice complete, obtain a passing fresh blind cross-review and passing bounded confirmations on the two hosts required by the repository's mandatory issue-confirmation policy, a monorepo-only control; their identities are recorded outside the public plugin tree. The public confirmation record names the revision, commands, bounds, and outcomes without publishing host identities. A blocked, unavailable, failed, or inconclusive gate is non-passing, prevents closure, and remains visible in that record. M5 GPU evaluations use the explicit two-host composition rule below to determine whether their GPU subtests form a passing confirmation.

## 2. Shared deliverables and work decomposition

### M0 — capability and semantics baseline

Create one versioned capability and semantics matrix in the public plugin documentation. It must list each frontend, property language, exploration backend, reduction, evidence class, and model class as supported, unsupported, experimental, or `delegated-integrated`. Each entry must name the effective semantics, version, limits, and regression fixtures. `delegated-integrated` means support through a named M3.0-compliant integrated backend with its restrictions and evidence. An unintegrated external alternative has status `unsupported` and may carry a see-also reference. A redirection alone is never product support. `experimental` is non-default, is marked in every result and user-facing surface, and cannot satisfy a mandatory milestone. It requires a recorded promotion and acceptance decision before it becomes supported or permits issue closure.

Split issue #11 into non-duplicating milestones only after checking the open tracker. Every milestone must name its parent workstream, its affected layers, a compatibility promise, explicit non-goals, and its exit evidence. Existing issues #3, #6, #7, #8, #10, and #17 remain references instead of being recreated.

Before classification, M0 reconciles every explicit issue #11 acceptance obligation to exactly one of: mandatory delivery through a named milestone or linked issue, deferred follow-up, or an out-of-scope decision explicitly approved by the tracker owner and recorded against issue #11. M0 records whether the opt-in arithmetic alternative is selected. Not selecting a tracker-required alternative is a deferral that requires the same tracker-owner scope decision. Every deferral or out-of-scope decision, including one made during M0 classification, requires an explicit tracker-owner scope decision that changes the parent issue's completion scope. An implementer may not narrow that scope by selecting only easier milestones.

**Acceptance evidence**

- A versioned matrix is linked from the README, skill workflow, and CLI or MCP reference material.
- A test checks that documented capability identifiers correspond to the declared CLI, MCP, and manifest surfaces. It validates the required status and evidence of every `delegated-integrated` entry, and verifies that every supported, experimental, or `delegated-integrated` entry references an existing fixture exercised by the test suite. Each experimental fixture asserts that the capability is off by default and carries an experimental marker in CLI, MCP, and report output.
- For every unsupported capability exposed through an applicable surface, a negative fixture asserts an explicit `unsupported`, `outside-subset`, or `not-executed` result rather than a verification verdict. An unsupported backend sub-capability has no verdict attributed to that backend, but an overall report may retain a verdict only from its separately identified supported effective backend. The matrix conformance test validates this attribution as well as status-consistent behavior and surface identifiers.
- The issue tracker has narrowly scoped children or linked milestones for every mandatory delivery item, plus the recorded mandatory, deferred, and out-of-scope set for issue #11.
- A versioned reconciliation table in `steps/issue-11-reconciliation.md` maps every explicit issue #11 obligation to a named mandatory delivery milestone or linked issue, deferred follow-up, or tracker-owner-approved out-of-scope decision. It records the arithmetic-alternative selection and links every deferred or out-of-scope decision to its tracker-owner scope decision.

### M1 — Promela compatibility and safe escape semantics

Deliver the following child milestones independently. Closing one child does not imply that another child or the wider Promela workstream is complete.

#### M1a — `unless` escape semantics

Finish the scoped `unless` milestone first. Freeze the accepted subset precisely, including brace-block shape, nesting policy, `atomic`, `d_step`, blocking operations, `timeout`, labels, and `goto`. Keep every unsupported shape an explicit `outside-subset` or `not-executed` result.

Issue #17 is this M1a escape-semantics slice. Closing it requires M1a's full evidence below and does not close M1b, M1c, or the broader Promela workstream.

**Acceptance evidence**

- BDD scenarios turn representative accepted `unless` inputs into executable checks with observable reports.
- Unit and directed tests cover guard priority, send and receive enabledness, `timeout`, escape labels, `goto`, both directions of `atomic` interaction, and the stated `d_step` policy.
- Differential tests against pinned SPIN 6.5.2 compare verdict and error class for small models, including the selected corpus examples, with the reference toolchain identity and compile flags recorded in the confirmation record. The SPIN and compiler identities are verified and rejected on mismatch before each bounded, isolated differential run. Each tool's witness replays on the other tool or an independent replayer under the recorded step-normalisation rule. State-count comparison is optional and uses partial-order reduction disabled plus a recorded normalisation rule.
- CLI, MCP, parser, schema, skill, reports, provenance, and subset probes expose the accepted subset consistently. Unsupported nested or other out-of-subset forms remain explicit refusals.
- Race, full, static, blind-review, and bounded two-host confirmation gates pass before closing issue #17.

#### M1b — arithmetic and semantic compatibility policy

Establish a versioned Promela compatibility policy. The strict arithmetic behavior remains the default. M1b includes implementation of an opt-in SPIN-compatible alternative only when it is selected as a supported capability. Otherwise it remains explicitly unsupported. A selected alternative requires a migration record, report field, and differential evidence against pinned SPIN 6.5.2 with the reference toolchain identity recorded in the confirmation record. Changing the default requires a separate versioned migration and an explicit report record.

**Acceptance evidence**

- Directed differential tests cover integer boundaries and every declared divergence.
- Each changed policy is opt-in or versioned, documented, and recorded in affected reports.
- When selected, the alternative has pinned SPIN 6.5.2 differential tests with toolchain identity and compile flags in the confirmation record, a migration record, and a report-field fixture. The SPIN and compiler identities are verified and rejected on mismatch before each bounded, isolated differential run. When unselected, its opt-in request has an `unsupported` fixture and, if it is tracker-required, a link to the M0 tracker-owner deferral decision.

#### M1c — embedded-C verification route

Decide one safe route for embedded C. Either route starts only after M1a and M1b have passed acceptance evidence. The M1c design record selects the restricted route only when its permitted effects can be fully tracked and isolated in-engine. It selects the SPIN-backed route when its verified immutable toolchain and M3.0 contract preserve the required property and evidence semantics. If both qualify, it records the selected route and why; if neither qualifies, M1c stays open or uses an M0 tracker-owner deferral while embedded C remains `unsupported`. A restricted embedded-C path must define permitted effects, state tracking, isolation, error handling, and source provenance. A SPIN-backed path may start only after M3.0 has supplied the backend contract. It must define translation, pinned version, property preservation, result translation, artifact retention, isolation, resource and cancellation limits, provenance, and failure mapping. The external SPIN and compiler toolchain must run in an isolated immutable image or through configured verified executables. Record its digest or verification identity in provenance and reject a mismatched identity before execution.

Neither route may execute user-supplied C on the host without isolation, a declared permitted-effect policy, bounded resources, cancellation, provenance, and explicit failure handling. Running arbitrary host C is out of scope, whether it is linked into this verifier or invoked through an external backend.

**Acceptance evidence**

- Closure records which route was selected and supports at least one declared C effect. A decision to support no C effects uses M0's explicit tracker-owner deferral process and retains `unsupported` status in user-facing material instead of closing M1c.
- The SPIN-backed route uses the accepted M3.0 contract. The restricted in-engine route satisfies the equivalent isolation, resource, cancellation, provenance, and failure controls specified here.
- Tests cover every supported C effect, hostile or unsupported input, isolation failures, toolchain-identity mismatch, timeout or cancellation, and backend failures.
- Unsupported C remains an explicit `not-executed` result and is never represented as simulated support.

### M2 — untimed Petri-net domain expansion

Extend the Petri frontend in dependency order.

1. Replace byte-only place capacities with checked finite token domains and an explicit versioned `unbounded` capacity form. Until M3.2 is available, `unbounded` input is system-level `unsupported`. The finite explicit-state engine always rejects it deterministically as `unsupported`, never with a verification verdict. The M2 CLI and MCP fixtures cover this finite-engine and system-unsupported path. This slice also has a CLI/MCP fixture for an ordinary P/T initial marking exceeding its declared finite capacity; it returns `invalid-input` with no property verdict before exploration. The capability matrix fixes these statuses for both CLI and MCP. Update the schema, IR, state encoding, transition execution, trace rendering, reports, and input validation together.
2. Add bounded inhibitor arcs with explicit zero-test semantics. Preserve the existing ordinary P/T behavior and distinguish a capacity bound from an enabling condition.
3. Add finite colours, bindings, guards, and multiset arc expressions. A coloured-place capacity bounds the total token-multiset size across all colours, not each colour independently. Reject input before IR lowering or unfolding when a finite coloured place's initial aggregate multiplicity exceeds its total capacity, an initial colour lies outside its declared finite domain, multiplicity arithmetic overflows, or an ordinary P/T initial marking exceeds a finite capacity; CLI and MCP return the named non-verdict `invalid-input` result. Statically reject an arc expression whose declared target colour is outside the finite domain, and reject at binding time any evaluated expression that produces an undeclared colour or overflowing multiplicity. For dynamic validation, candidate derivation is marking-dependent and versioned: in a marking reached through prior valid firings, derive the finite set of binding-variable valuations by a versioned consistent join over declared input-variable positions against tokens present in the marking: repeated occurrences of one variable must match the same typed token value, distinct variables use the specified cross-product, and required input multiplicities constrain derivation only where their pattern positions are declared. This derivation is intentionally weaker than final enabledness and occurs before evaluating guards or arc expressions. Every binding variable must appear in a matchable declared input-variable position; otherwise static validation rejects the transition as `invalid-input`. Guards and expressions may read only the derived valuation and transition constants; marking-read variables and marking-dependent arc multisets are outside the initial finite-unfolding subset and return `unsupported` until a separately specified encoding preserves source-binding identity and fairness. A derived candidate in that marking is validation-reachable independently of final firing eligibility. A binding behind an invalid predecessor is not validation-reachable because invalid bindings have no successor. Inspect it in this mandatory order: evaluate its guard and classify any domain or overflow error as an eligible binding-time rejection; only a successfully evaluated true guard then permits evaluation and range-checking of every input and output expression without enabledness short-circuiting, followed by token-availability testing and, only if enabled, successor production. A successfully false guard produces neither a rejection nor a successor. Any invalid binding has no successor, and reachability validation continues over valid firings only. The versioned canonical tuple comparator is lexicographic over canonical UTF-8 transition ID, declared binding-variable order with canonical typed value encoding, then normalized source-file path and byte offset. A reachable binding-time rejection is collected with its binding and source identity; no property verdict may publish until complete reachable-binding validation succeeds, unless static range analysis proves every evaluated expression range-safe. The request returns the named non-verdict `invalid-input` only after complete validation (or an early-stop proof that no unvisited validation-reachable marking can yield a tuple less than the retained tuple under the versioned comparator) establishes the canonical least reachable `(transition ID, binding serialization, source location)` tuple, deterministically across exploration order and worker count. If validation cannot finish at a resource limit—even after observing a noncanonical invalid binding—it returns the named non-verdict resource stop with no authoritative invalid-binding tuple and no property verdict. Reachable-binding validation runs on the unreduced model unless static range analysis proves safety; any reduction used for it must preserve the complete reachable invalid-tuple set needed to derive the canonical least tuple and the `invalid-input` outcome, with directed fixtures for property-preserving reductions that would otherwise prune the only invalid binding or the canonical least of two invalid bindings. Static schema/domain validation runs before capability negotiation, so malformed input is `invalid-input` even when it also selects an unsupported capability. Dynamic binding validation runs only after a negotiated executable capability; an unsupported coloured combination returns `unsupported` unless static validation already rejected it. Preserve a valid capacity during finite unfolding with a shared capacity-control construction (for example, a complementary free-slot place), rather than assigning the full capacity to every unfolded colour place. Every generated colour place has a finite per-place bound equal to the source total capacity, and the shared free-slot place starts with the source total capacity minus the source initial aggregate marking and enforces the actual aggregate bound. For each binding and coloured place, capacity-control arcs represent the binding's net token-count change: they consume free slots only for positive net production and return slots only for net consumption, so a full-place recolouring or weighted self-loop with zero net change remains enabled. Preserve colour and source identity in witnesses. Transition fairness ranges over each transition-binding element; unfolding maps every binding element to its corresponding P/T transition. The capability matrix and every coloured-net report name this fairness granularity. Coloured nets with an `unbounded` source place are outside finite unfolding and M3.2 until a separate encoding is specified; CLI/MCP return `unsupported` and the M0 reconciliation table records that boundary. Coloured nets combined with inhibitor arcs remain unsupported until separately specified.

Version every affected Petri schema and persisted artifact when the capacity representation changes. Preserve existing ordinary P/T inputs and fixtures where compatible. Otherwise provide a documented migration or a deterministic, documented rejection for an old artifact that cannot be interpreted safely.

Transition-level fairness for ordinary, capacity-bounded, and inhibitor P/T nets, terminal markings, and the closed Petri findings remain regression requirements. They must not be weakened while extending those input classes.

**Acceptance evidence**

- Fixtures cover capacities above 255, overflow boundaries, weighted self-loops, zero tests, competing transitions, and intended terminal markings.
- Transition-level fairness regression fixtures cover ordinary, capacity-bounded, and inhibitor P/T nets. Binding-level fairness regression fixtures cover coloured nets.
- A coloured-net fairness fixture distinguishes binding-level fairness from transition-level fairness and asserts the declared binding-level result.
- An independent marking enumerator validates small ordinary, inhibitor, and coloured examples.
- Each finite-colour fixture without inhibitor arcs has a correct unfolded P/T comparison. A capacity-two, two-colour fixture proves that unfolding enforces a total capacity of two rather than allowing two tokens of each colour, while a full-place recolouring and a weighted self-loop with zero net place change remain enabled. Both cases compare the independent marking enumerator with the unfolded P/T result.
- A CLI/MCP validation matrix covers initial aggregate and ordinary P/T finite-capacity excess, initial and static arc-target out-of-domain colours, multiplicity overflow, and binding-time out-of-domain or overflow expressions; every case asserts `invalid-input`, no surviving property verdict, and identical behavior under differing exploration orders and worker counts. CLI/MCP fixtures include at least two reachable invalid bindings whose discovery order changes by worker count or search order, including a guard-overflow case competing with another reachable invalid binding; invalid input and output expressions both with and without another unsatisfied input arc; and a binding only otherwise reachable behind an invalid predecessor, which is not validation-reachable because invalid bindings have no successor. They also include a resource limit reached after a noncanonical invalid binding is observed; successful false guards shielding otherwise invalid input and output expressions; early noncanonical enumeration rejection; property-preserving reductions that would prune the sole invalid binding or canonical least of two invalid bindings; static range-analysis safety, boundary failure, and equivalence with dynamic validation on small enumerable models; static rejection of output-only, guard-only, and non-pattern-only variables (where “non-pattern” means syntactically absent from every declared input-variable position), plus an initially empty but later populated input place accepted through dynamic derivation; and `unsupported` marking-dependent arc multiset/guard cases with a fairness comparison against the finite-unfolding boundary. Canonical cases return the canonical `invalid-input` tuple, the limit case returns only the named resource stop, and false-guard cases have no successor from that binding and retain the expected result from other valid firings. A combined malformed coloured-unbounded input confirms schema/domain `invalid-input` precedence over `unsupported`. A separate unsupported coloured combination containing a non-static invalid expression asserts `unsupported` without dynamic binding evaluation. Finite-colour unfolding fixtures also reach two tokens of one colour in a capacity-two, two-colour place.
- A versioned explicit-backend fixture targets the finite explicit-state engine and asserts the matrix-defined `unsupported` result for `unbounded` capacity through CLI and MCP; a routing migration never changes that fixture. A separate versioned default-route fixture sends a request without explicit backend selection and asserts its matrix-defined route. A routing migration updates that default-route fixture and the matrix routing status together.
- A coloured net with an inhibitor arc returns the matrix-defined `unsupported` result through CLI and MCP, and appears in the M0 reconciliation table as mandatory with a named delivering milestone, deferred, or out-of-scope with the tracker-owner decision.
- Compatibility tests cover existing Petri inputs, versioned schemas, persisted reports or traces, migrations, and deterministic rejection of unsupported legacy artifacts.

### M3 — capability-aware verification backends

#### M3.0 — backend contract

Introduce the backend contract before implementing any new verification class or specialized external backend. The versioned contract must carry canonical model/property identities derived from the submitted IR and normalized property, model and property translation, capability negotiation, configured bounds, exact or approximate numerical evidence, trace or certificate availability, backend version, cancellation, isolation requirements, provenance, and explicit error classes. Every certificate validator and independent oracle binds those identities and either uses trusted in-process translation or verifies translation equivalence independently. It defines the complete terminal status set, including the named non-verdict `resource-stop`; the allowed terminal-status × numerical-evidence-class × trace-assurance combinations; and the required report fields for each terminal exit, so a backend exit cannot be silently converted into a property verdict. A `resource-stop` report records the limiting resource or budget, consumed amount, phase, and declares that no invalid-binding tuple or property verdict is authoritative; M2, M4, M5, and their fixtures use this exact identifier. The versioned trace-assurance field is independently `replayed`, `not-applicable`, `trace-absent-approved`, or `replay-unavailable-approved`; `not-applicable` is permitted for any terminal outcome whose declared property/result class has no trace contract, including non-verdict exits, certificate-only outcomes, and an exact verified result with no witness or trace requirement, while the latter two values include the approved exception identity. Numerical evidence remains unchanged by an approved trace exception. An approximate violation may be `violated` only with numerical evidence `approximate` and trace assurance `replayed` through an independently replayed witness; an approximate non-violation is a non-verdict `inconclusive` result with numerical evidence `approximate` and normally trace assurance `not-applicable`. An independently approved oracle-validation exception may replace only that numerical-evidence value with `oracle-exception-reduced`; trace assurance remains one of its declared values, normally `not-applicable`. It is never `verified`. The versioned numerical-evidence enumeration is `exact`, `approximate`, `certified-sound`, and `oracle-exception-reduced`; `oracle-exception-reduced` is distinct from `approximate`, is permitted only for the contract's enumerated non-verdict terminal-status and trace-assurance combinations, and records its approved oracle-validation exception identity. `certified-sound` numerical evidence is distinct from approximate evidence and requires exact rational arithmetic or a sound outward-rounded interval method. An M3.4 `exact` numerical result is a certified-sound exact-rational form: it carries the same independently validated model/property binding and required least/greatest-fixpoint or scheduler-optimality proof, rather than bypassing numerical-correctness validation. A `certified-sound` report carries either an exact rational solution certificate checked independently against the declared model equations and property calculation, or an interval representation with independently checked lower and upper fixpoint certificates against those equations; every proof schema and validator also establishes the property's required least or greatest semantic fixpoint and, for an MDP, the declared scheduler optimum. It also declares the versioned checker algorithm, rounding semantics, and property-operator consistency data. The contract version fixes the proof schema and validator inputs for each form. Missing, malformed, failed, or numerically inconsistent proof validation is `contract-invalid` with no property verdict. Each backend report and capability-matrix entry records the contract version it implements.

**Acceptance evidence**

- Contract tests cover unsupported capability, invalid input, cancellation, isolation refusal, backend failure, result translation, contract-version propagation, and exact-versus-approximate numerical-evidence translation, including an approximate-evidence harness result. They enumerate every terminal-status × numerical-evidence-class × trace-assurance combination and every negotiated capability combination, accepting only entries declared by the versioned contract; every undeclared combination or evidence-capability escalation deterministically becomes `contract-invalid` with no property verdict.
- A minimal out-of-process conformance-harness backend can return valid exact verification and violation results, an approximate violation with a replayable witness, an approximate non-violation, a certified-sound inconclusive result, or can hang, crash, exceed its budget, or return a mismatched identity. It also emits invalid protocol combinations—`verified` with approximate numerical evidence, approximate `violated` without an independently replayable witness, an undeclared evidence-capability or trace-assurance escalation, and falsely labelled, missing, malformed, or numerically inconsistent `certified-sound` evidence including a failing rational-solution or interval-fixpoint proof, an equation-valid but non-least/non-greatest solution, a non-optimal MDP scheduler, or a valid proof and oracle agreement bound to a substituted model or property—which deterministically convert to the named non-verdict `contract-invalid` terminal status with no property verdict. Contract tests use it to prove result, resource, cancellation, isolation, provenance, proof validation, and failure behavior before later contract consumers exist.
- The conformance harness exercises every documented terminal contract exit and asserts the corresponding report status, evidence class, and backend identity. A verdict-bearing exit must carry its correct property verdict and declared trace or certificate availability; a non-verdict exit must carry no property verdict. Its captured exit evidence is retained in the M3.0 milestone confirmation record.

#### M3.1–M3.4 — verification classes

Deliver the following as separate milestones with independently reviewable semantics.

1. **Exact symbolic finite-state verification** — declare the supported IR and property subset, produce replayable counterexamples for every supported violating property class except where the shared trace-exception process has passed, and compare its results with the explicit engine on small models.
2. **Unbounded P/T-net analysis** — consume the versioned `unbounded` Petri capacity form and support only selected decidable questions such as coverability and boundedness. Keep coverability separate from exact reachability and reject inhibitor-net or arbitrary-program claims outside the chosen decidable class. Declare whether finite-colour input is rejected or unfolded for a specified finite subclass. When unfolding is supported, record the transformation and resulting bounds in the report.
3. **Timed verification** — use IR-level timed fixtures through a named versioned timed-model schema accepted by CLI and MCP, then define clocks, zone or region representation, urgency, Zeno behavior, time divergence, and the accepted property language. Its capability-matrix frontend entry and acceptance evidence cover that schema, CLI, and MCP exposure. It does not depend on M2T fixtures.
4. **Probabilistic verification** — use IR-level DTMC or MDP fixtures through a named versioned probabilistic-model schema accepted by CLI and MCP, then define scheduler assumptions, numeric precision, threshold interpretation, and independent validation of probability results. A threshold result uses `certified-sound` evidence only from exact rational computation or a sound outward-rounded interval method. For the property's comparison operator, an exact value or every interval point satisfying it is `verified`, every point failing it is `violated`, and an interval containing both satisfying and failing values is `inconclusive`. Fixtures cover equality boundaries for `≥`, `>`, `≤`, and `<`; a decisive `certified-sound` result with an approved trace-assurance exception; and preservation of `certified-sound` numerical evidence for verified, violated, and inconclusive outcomes. Independent probabilistic validation remains required. Its capability-matrix frontend entry and acceptance evidence cover that schema, CLI, and MCP exposure.

A specialized external tool may be integrated only through this contract. Redirecting a user to another product does not complete a milestone.

**Acceptance evidence for every backend**

- Positive and negative fixtures, documented restrictions, and a capability-matrix entry.
- Comparison with an independent oracle, certificate, or validated explicit encoding is required by default. M3.1 uses the explicit engine on small models, M3.2 uses an independently checked certificate or second implementation, M3.3 uses a validated timed encoding or named timed oracle, and M3.4 uses a named independent probabilistic oracle such as PRISM. For M3.4, the oracle records exact or sound-interval mode and error settings. A decisive backend verdict passes only when a decisive oracle has the same operator-aware verdict; an ambiguous oracle interval is non-passing for a decisive backend claim. A non-decisive backend `inconclusive` result may pass numerical validation when its required exact-value equality/containment or sound-interval overlap condition holds, regardless of whether the oracle is decisive or ambiguous; it remains `inconclusive` and is never upgraded to the oracle's verdict. Fixtures state this expected outcome for decisive-oracle/inconclusive-backend and ambiguous-oracle/inconclusive-backend cases. For every certified-sound backend result—`verified`, `violated`, or `inconclusive`—when both sides supply exact values, they must be equal; when exactly one side supplies an exact value, that value must lie in the other side's interval; when both sides supply sound intervals, they must overlap; a decisive backend result must additionally agree under the property's comparison operator with a decisive oracle, while a non-decisive backend result remains `inconclusive` after a valid overlap; otherwise the result is non-passing. Fixtures cover decisive-oracle/inconclusive-backend, ambiguous-oracle, exact-backend/sound-interval-oracle, and unequal-exact-values-with-the-same-threshold-verdict cases. An oracle or trace exception requires written rationale in the milestone confirmation record and approval by the closure reviewer and tracker owner. The report and capability matrix identify the exception type and linked approval. An oracle-validation exception is available only for M3.0's enumerated non-verdict terminal-status and trace-assurance combinations; it uses the distinct reduced numerical-evidence class, may not label the result exact or exhaustive, and cannot waive any decisive-oracle requirement or permit a verdict-bearing exit. A trace exception records only the separately declared trace-assurance value and preserves the result's numerical evidence. The oracle exception is unavailable to M3.4; only a trace exception may apply. The probabilistic backend always retains its stated independent-validation obligation.
- Explicit reports for missing capability, invalid model, backend failure, cancellation, and numerical ambiguity.
- Visible limits and approximations. Exact exhaustive evidence is never reused for an approximate result.
- For M3.2, rejected finite-colour input has an explicit `unsupported` fixture. When a finite subclass is unfolded, fixtures compare it with the M2 unfolded P/T cases and verify that the report records the transformation and bounds.
- Unbounded inhibitor-net input returns the matrix-defined `unsupported` result through CLI and MCP and appears in the M0 reconciliation table as mandatory with a named delivering milestone, deferred, or out-of-scope with the tracker-owner decision. General unbounded inhibitor-net questions are out of scope unless a named milestone defines a decidable subclass.
- M3.2 CLI and MCP fixtures cover either explicit selection or the versioned routing migration, plus an out-of-capability property returning the matrix-defined `unsupported` result. With explicit M3.2 selection, they assert that a request without explicit backend selection follows the separate finite-engine default-route fixture and returns `unsupported`. With a versioned routing migration, they instead assert that a request without explicit backend selection routes to M3.2, and the same change updates that default-route fixture and the capability matrix together; neither path changes an explicitly finite-engine request.
- A violation has a counterexample replayed on the explicit engine or an independent replayer under the backend's declared semantics. For unboundedness, evidence may be an independently checked self-covering witness, pumping construction, or certificate that establishes the reported result. In a mixed finite/unbounded net, the pump segment end marking must equal its start marking for every source finite-capacity place and be greater than or equal to it for every declared-`unbounded` source place, with at least one strict increase. The certificate includes a legal prefix from the initial marking to the pump start and a legal pump firing sequence; every prefix and pump intermediate marking is checked under source capacities. A regression fixture rejects a segment whose prefix exceeds a finite capacity. A capacity-preserving encoding with complementary places may supply the same proof. Regression nets reject both a changed finite capacity-one `p` with an increasing unbounded `q`, and a segment that increases unbounded `q1` while decreasing unbounded `q2`. For boundedness, including violation of an unboundedness property, evidence is an independently checked boundedness certificate. A finite-capacity replay is evidence only for coverability or reachability witnesses: it raises only source places declared `unbounded` to at least their witness peak, preserves every source finite capacity, and rejects a witness exceeding a preserved finite capacity. The report records the chosen capacities. A mixed finite/unbounded regression fixture proves that an invalid witness cannot replay by raising an original finite capacity. When an unbounded-place peak exceeds the explicit engine's maximum finite domain, replay uses the independent replayer or the trace-exception process. M3.3 uses symbolic timed traces replayed under its declared semantics; M3.4 uses an independently validated scheduler, sub-model, or witness set. Reports and the capability matrix distinguish exception types. An approved oracle-validation exception uses the declared reduced numerical-evidence class and may not be labelled exact or exhaustive; an approved trace/replay exception records only the trace-assurance value and approval identity, distinguishing an absent trace from an existing trace whose required replay cannot be provided, and does not replace or downgrade numerical evidence. A trace or replay exception never waives M3.0's independently replayed-witness requirement for an approximate violation: an approximate violation without that replay is always `contract-invalid` with no property verdict. In particular, decisive M3.4 `certified-sound` and exact results with an approved trace exception retain their numerical evidence and carry their separately approved trace-assurance value.

### M2T — timed Petri-net semantics

Begin timed Petri-net work only after M2 untimed Petri semantics and M3.3 have passed their acceptance evidence. M3.3 supplies the clock model, zone or region representation, urgency, Zeno behavior, time-divergence policy, and timed property language. Integrate Petri delays and clocks through that semantics instead of a time-erased translation.

**Acceptance evidence**

- Timed Petri fixtures exercise actual clock and delay behavior, including urgency and time-divergence boundaries.
- Small timed nets are checked against an independent oracle or a validated timed encoding under the same declared semantics.

## 4. Per-milestone implementation checklist

For each child milestone, use this sequence.

1. Write the design record with scope, semantic contract, preserved invariants, non-goals, budget policy, and acceptance cases.
2. Add a failing Gherkin scenario under `features/` and focused unit or oracle tests in the lowest affected package.
3. Implement the smallest lower-layer change. Keep `internal/spike` out of production dependencies.
4. Update CLI, MCP, reporting, skill, documentation, fixtures, and manifest declarations together when the observable contract changes.
5. Run focused tests, then the full engine suite, `go vet ./...`, formatting checks, and relevant SPIN, race, security, backend, or benchmark gates.
6. Record a confirmation document under `steps/` with commands, outcomes, assumptions, limits, measurements, deferred work, and the acceptance result.
7. Obtain a passing fresh blind cross-review and passing bounded confirmation on both hosts required by the repository's mandatory issue-confirmation policy before closing the milestone. Record unavailable, failed, blocked, or inconclusive gates honestly as non-passing and keep the milestone open. M5 GPU evaluations apply their explicit two-host composition rule when determining whether GPU subtests form a passing confirmation.
