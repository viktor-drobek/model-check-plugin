# Spike — подтверждение (протокол, п. 6)

Шаг: **Spike** (план 14 §9). Критерий выхода: «Замеры получены; оценки G0–G4 пересчитаны по ним; решение о продолжении зафиксировано».

**Соответствие критерию выхода: выполнен**, с оговоркой по второму пункту: замеры дают основание пересчитать G0–G1 и уточнить A4; для G2–G4 spike не даёт данных, и их оценки предлагается оставить без изменения — это тоже «пересчёт по замерам», но с нулевой поправкой, что ниже сказано явно.

## 1. Что сделано

- `features/spike-explorer.feature` — написан до кода; 10 сценариев (petrinet1: тупик с witness `t1, t4` и полный обход = 6 маркировок; mutex_flaw: нарушение `assert(cnt == 1)` и полный обход = 429 состояний как у `pan -c0`; детерминизм (3 примера); синтетическая модель 1e5 состояний в бюджете; исчерпание бюджета → `inconclusive`; нарушение + частичный обход → `violated` с `complete=false`).
- `engine/internal/spike/` — калибровочный explorer: плоский байтовый вектор, детерминированный DFS с явным стеком, тупик = нет разрешённых переходов, проверка assert как свойство перехода, бюджеты по состояниям и времени, `Replay` свидетельства. Два множества посещённых: `map[string]struct{}` (baseline) и компактная open-addressing таблица 64-битных хешей с ареной полных векторов (точный режим по 14 §4.1). Модели захардкожены: `petrinet1.go`, `mutex_flaw.go` (сверена с `pan -d` при `-o1 -o2 -o3`), `counters.go` (K^N состояний). `cmd/spike` печатает states/s, удержанные байты/состояние, peak RSS.
- `engine/steps_spike_test.go` — step definitions через `stepRegistrars`.
- `engine/internal/spike/testdata/counters.pml` — Promela-версия синтетической модели для оракула.
- `steps/spike-logika.md` — ревью; 5 находок, 4 исправлены, 1 оставлена с оговоркой.
- Зависимости не добавлялись. SPIN 6.5.2 установлен `sudo apt-get install -y spin` (успешно с первой попытки; исходники с GitHub не понадобились).

## 3. Замеры

Машина: linux/arm64, 8 ядер, 11 ГБ RAM; Go 1.26.0; SPIN 6.5.2; `gcc -O2 -DNOREDUCE`; pan с `-m2500000 -w26` для counters (иначе `-m` по умолчанию обрезает поиск — первая серия замеров с `-m100000` дала 762 713 вместо 1 000 000 состояний и отброшена). Времена одиночных прогонов; разброс между прогонами spike ±20 % (1e6: 1.33 с и 1.66 с в двух запусках с map).

### 3.2. Скорость и память

| Модель (состояний) | Движок | states/s | байт/состояние (удержано под хранение) | peak RSS |
|---|---|---|---|---|
| counters 1e5 | pan | 0.91 M | 41 («actual memory usage for states» 4.1 МБ) + фикс. 512 МБ хеш-таблица `-w26` + 134 МБ стек | 667 МБ |
| | spike, map | 1.13 M | 51 | 87 МБ |
| | spike, compact | 0.85 M | 37 | 90 МБ |
| counters 1e6 | pan | 1.30–1.41 M | 38 (38.4 МБ) | 703 МБ |
| | spike, map | 0.60–0.75 M | 72 | 906 МБ |
| | spike, compact | 0.79–0.88 M | 32 | 803 МБ |
| counters 2.1e6 | pan | 1.05–1.08 M | 46 (96.3 МБ) | 762 МБ |
| | spike, map | 0.40–0.61 M | 69 | 1.82 ГБ |
| | spike, compact | 0.72–0.77 M | 32 | 1.73 ГБ |
| mutex_flaw 429 | pan `-c0 -w18` | 10 прогонов: 0.01 с wall | 0.29 МБ states, 2.7 МБ всего | 6 МБ |
| | spike | 1 мс/прогон, 10 прогонов 0.01 с | 162 (map) / 83 (compact) | 3.3 МБ |

Что видно:
- **Ядро обхода на Go на 0.8–2.2× медленнее pan** (лучший случай — быстрее на 1e5 с map; худший — map на 2.1e6). Порог K1 «медленнее в 50 раз» не достигнут и близко; на самой `mutex_flaw` отношение неизмеримо — оба укладываются в ~1 мс, время процесса доминирует.
- **Память под хранение** сопоставима с pan: 32 байт/состояние у compact против 38–46 у pan при векторе 5–7 байт (у pan вектор 44–60 байт — он хранит заголовки процессов; у spike их нет, так что «байт на состояние» сравнимы только как накладные расходы структуры, не как сжатие).
- **Peak RSS spike в 10–25 раз больше удержанной памяти** (0.8–1.8 ГБ на 1–2e6 состояний). Причина установлена: DFS на counters идёт цепочкой глубиной = числу состояний, а spike материализует все N преемников каждого кадра стека (1.2–1.3 M аллокаций на 1e5 состояний по `go test -bench`). Это артефакт spike, не свойство подхода: pan при той же глубине держит 134 МБ стека при `-m2500000`. Для G0 обязательна ленивая генерация преемников (в кадре — индекс перехода, не список).
- Компактная таблица медленнее map на 1e5 (рост таблицы с 1024 слотов удвоениями + `maphash`), быстрее на ≥1e6 и вдвое экономнее по памяти.

### 3.3. Что spike НЕ измеряет (честно)

- Интерпретацию IR: модели скомпилированы в Go так же, как pan компилирует C. Множитель интерпретации не измерен; по опыту интерпретаторов охраняемых команд — 3–10×. Это главная неизмеренная величина K1.
- Реальные векторы состояния (каналы, несколько процессов с локальными): вектор 5–7 байт против типичных 30–100.
- BFS, параллелизм (8 ядер не использованы), контрпример с обратным отображением, переполнение `byte` (не проверяется в spike; в G0 — `invalid-model` по плану).

## 5. Рекомендации по оценкам G0–G4 и по A4 (план 14 не правлю — предложения владельцу)

- **G0 (8–12 pd): оставить 8–12**, но зафиксировать в содержании три пункта, выявленных spike: (а) ленивая итерация преемников в кадре DFS и отдельный бюджет глубины (иначе 1 ГБ исчерпывается стеком на глубине 1e6); (б) компактная хеш-таблица с ареной как режим по умолчанию, map — только как эталон в тестах; (в) поле `complete` в отчёте рядом со статусом (найдено ревью: `violated` при прерванном обходе даёт частичное `states_stored`).
- **G1 (12–18 pd): поднять до 14–20** (+2 pd). Основание: ручная кодировка `mutex_flaw` потребовала сверки гранулярности операторов с `pan -d` (инициализация `me` — не шаг; `goto` сливается с guard; `cnt++`, `assert`, `cnt--` — три шага). Совпадение счётчиков с SPIN по §8.1 зависит от воспроизведения этих правил в frontend; нужен инструмент сравнения таблицы переходов с `pan -d`, которого в плане нет.
- **G2, G3, G4: без изменений** — spike не даёт по ним данных. Единственное касание G3: трактовка `evidence=exhaustive` для `violated` (свидетельство — точный прогон) должна быть записана в `evidence-and-status.md`, иначе поле будут читать как «покрытие поиска» (ревью, находка № 5).
- **A4 («малая/средняя модель»)**: предложить числа — *малая*: ≤ 1e5 состояний и глубина ≤ 1e5 (≤ 2 с даже при 10× интерпретации; память < 50 МБ); *средняя*: ≤ 1e6 состояний, глубина DFS ≤ 1e6, вектор ≤ 128 байт — ориентир 60 с / 1 ГБ сохраняется; *большая*: всё сверх — `mc_estimate` предупреждает, `mc_check` отдаёт `inconclusive` по бюджету. Добавить в A4 глубину как отдельную границу: замеры показали, что стек, а не таблица, первым упирается в память. Проверка на `CH15` и `CH9/leader.pml` с ростом N (как в плане) остаётся — spike их не трогал.

## 6. Решение: **продолжать (go) — переход к G0**

Основания: (1) ядро обхода на Go по скорости в пределах 2× от pan и по памяти хранения сопоставимо — запас на интерпретацию IR есть даже при 10×; (2) методика сравнения с pan отработана и воспроизводима (три модели, счётчики совпали); (3) обнаруженные дефекты (стек, полнота отчёта) — конструктивные и закрываются в G0 известными приёмами. Условия: G0 включает ленивую генерацию преемников и бюджет глубины; первый замер интерпретируемого IR на `counters` и `mutex_flaw` делается в G0 и сравнивается с этими числами — если интерпретация даст > 20× к ядру, A4 пересматривается до G1.

## 7. Отложено и почему

- Замер интерпретации IR — нет IR (по определению spike).
- Peak RSS pan на mutex_flaw/petrinet1 в сопоставимых условиях — не информативно (оба < 10 МБ, доминирует `-w`).
- Проверка переполнения `byte` в Petri-кодировке — G0 по плану.
- Дифференциальный тест как автоматический (запуск `spin`/`pan` из `go test`) — не сделан: по плану это CI; здесь числа pan вписаны в feature как константы с указанием версии SPIN и флагов.
- Многократные прогоны и статистика разброса — только по 2 прогона на конфигурацию; числа даны диапазоном.
